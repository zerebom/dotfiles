# Claude Code Configuration

このファイルはClaude Codeの動作設定を定義します。

## コマンド実行の標準

### 日付取得
- **CRITICAL**: 日付取得は常に `/bin/date` を使用すること
- `date` コマンドは使用しない（PATH設定により予期しないエラーが発生する）
- 例: `/bin/date +%Y-%m-%d` （今日の日付を YYYY-MM-DD 形式で取得）

## cmux + Worktree 並列運用

cmux（ターミナルマルチプレクサ）と worktree を組み合わせて、複数の Claude Code セッションを並列実行できる。
詳細なコマンドリファレンスと手順は **[docs/cmux.md](docs/cmux.md)** を参照。

### いつ並列実行を提案する？ — 積極的に・即座に
**CRITICAL**: 分割可能と判断したら、ユーザーに聞かれる前にAI側から即座に提案すること。「できそうだけど黙っている」は禁止。

以下の状況を検知したら **その場で** 分割提案する：
- 緊急割り込み（hotfix等）で現在の作業を中断する必要がある時
- 独立した複数タスクを並列で進められそうな時
- 長時間かかるタスク（見積もり10分超）を任された時
- タスクの中にファイル競合しない独立サブタスクが2つ以上ある時
- ユーザーが「あれもこれも」と複数の依頼を一度に出してきた時

### 提案の仕方 — 具体的な分割案をセットで出す
分割可能と判断したら、**待たずに** 以下のフォーマットで提案する：

```
🔀 並列実行できそうです：
- セッションA: 〇〇（対象ファイル: ...）
- セッションB: △△（対象ファイル: ...）
ファイル競合なし。cmux で分割しますか？
```

ポイント：
- 分割案は具体的に（何をどのセッションでやるか、対象ファイルは何か）
- ファイル競合の有無を明示する
- ユーザーが「はい」だけで進められるレベルまで詰める

### ツール
- **cmux**: ターミナルマルチプレクサ CLI（サーフェス作成・画面読み取り・コマンド送信）
- **ccmanager**: 並列セッション管理UI（`ccmanager`で起動）
- **wtp**: worktree作成（`wtp add feature/xxx`）

### CRITICAL
- cmux 内で tmux を起動しない（ソケット認証が壊れる）
- 並列セッションは必ずユーザー承認後に起動する

## Python環境の標準

### uv + pyproject.toml
- **パッケージマネージャ**: `uv` を使用する（pip, poetry ではなく）
- **スクリプト実行**: 直接 `python` を叩かず `uv run python` 経由で実行
- **依存追加**: `uv add {package-name}`
- **同期**: `uv sync`
- **アドホックな実験コード**: `codes/{project-name}/` 配下にプロジェクト単位で配置

## 検証ルール

### E2E検証の必須化

- **API/バックエンドのテストだけでは不十分**
  - curlやAPIクライアントでのテストはバックエンド動作の確認のみ
  - フロントエンド（ブラウザ）での実際の動作は別途確認必須

- **ストリーミング/リアルタイム機能の検証**
  - SSE、WebSocket、ストリーミングレスポンスは必ずブラウザで確認
  - curlでSSEイベントが送信されていても、ブラウザで段階的に表示されるとは限らない
  - DOM更新のタイミング、JavaScriptイベントループの影響を考慮

- **検証手順の明文化**
  - プロジェクト固有の検証手順は `steering/` に記載
  - ユーザーが実際に確認できる具体的な手順を用意
  - 期待される結果と失敗時の結果を明記

### 誤った検証の防止

- curlでバックエンドが正常でも「検証完了」としない
- 「動いているはず」ではなく「動いていることを確認した」まで実施
- ユーザーに検証してもらう手順を用意してから「完了」とする

## 実装アプローチの原則

### 本質的な解決を優先する

- **ログ仕込みとデバッグは最小限に**
  - 問題の深掘り・検証に時間をかけすぎない
  - 本質的な解決策（アーキテクチャ変更、ライブラリ活用）を優先する
  - 「なぜ動かないか」より「どう動かすべきか」を考える

- **既存実装に引きずられない**
  - 今の実装を修正しようとするより、あるべき姿を設計する
  - フレームワークやライブラリの標準的な使い方を優先する
  - 「今あるコードを活かす」より「正しい実装」を選ぶ

- **ユーザーのヒントを素直に受け入れる**
  - ドキュメントや代替手段を提示されたら、まずそれを試す
  - 自分のアプローチに固執せず、提案された方法を検討する
  - 「これまでやってきたこと」を捨てる勇気を持つ

### steeringベースの計画的実装

- **実装前にsteeringを更新**
  - コードを書く前に `steering/tasklist.md` を更新する
  - 実装方針・設計をドキュメント化してから実装に入る
  - 大きな方針転換は必ずsteeringに記録する

- **計画なしの試行錯誤を避ける**
  - 「とりあえず試す」を繰り返さない
  - 複数の修正を行う前に、全体の方針を決める
  - タスクの優先順位を明確にして、順番に実施する

## 🔧 自己修正ルール

### ツール実行エラー時の対応
コマンドやツールの実行でエラーが発生した場合：
1. **エラーを記録**: どのコマンド/ツールで何が失敗したかを把握
2. **回避策を実行**: その場では別の方法で目的を達成
3. **修正提案**: 作業完了後、「今後このエラーを回避するため、コマンド定義を修正しても良いですか？」とユーザーに確認
4. **自己修正**: 承認されたら該当ファイルを修正

**例**:
```
❌ date コマンドでエラー → /bin/date で回避
✅ 作業完了後:「今後 /bin/date を使うよう設定ファイルを修正しても良いですか？」
```
