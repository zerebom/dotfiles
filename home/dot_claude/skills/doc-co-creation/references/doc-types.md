# ドキュメント種類別ガイド

ドキュメントの種類ごとに、推奨する構成と書き方のポイントをまとめる。

---

## 技術ブログ・解説記事

**目的**: 読者に新しい知識や手法を伝え、実践できるようにする

**推奨構成**:
1. 導入（問題提起・読者の共感を得る）
2. 解決策の提示（What）
3. 仕組みの説明（How/Why）
4. 具体例・実演
5. まとめ・次のステップ

**書き方のポイント**:
- 問題提起から始め、読者が「自分ごと」と感じられるようにする
- 段階的に深掘りする（概念→仕組み→具体例）
- スクリーンショットやコード例で視覚的に補強する
- 専門用語は初出時に簡潔に説明する

**良い例**:
```
業務でAIを活用しよう、と日々腐心してますが、実際に業務効率化をしようとすると、
思っている以上に難易度が高いと感じる場面が多くあります。
```
→ 読者の共感を得る導入。主観を「感じる」と明示。

## 戦略ドキュメント・計画書

**目的**: 意思決定者が方向性を理解し、判断できるようにする

**推奨構成**:
1. エグゼクティブサマリー（1ページで全体像）
2. 現状認識（数字と事実ベース）
3. 目標（具体的・測定可能）
4. 施策（目標達成のための手段）
5. リスクと対策
6. スケジュール・マイルストーン

**書き方のポイント**:
- フレームワークは手段であり目的ではない。無理に当てはめない
- 略語・造語は初出時に必ず定義する
- 願望と事実を明確に区別する（「〜する予定」「〜を目指す」と「〜である」）
- 数字には根拠を添える

**避けるべきパターン**:
```
❌ 悪い例:
- **KR4（CS 効率）**: 月次/CEP案件 1 社あたりの CS 工数が、平均 **40h → 25h 以下**。
```
→ CEPの定義なし、40h→25hの根拠なし、太字の過剰使用

```
✅ 良い例:
- CS工数目標: 月次レポート作成を40h/社から25h/社に削減
  - 根拠: 期間比較機能により集計作業が自動化され、推定15h削減
  - 前提: 2026Q1に期間比較ビューをリリース
```

## 議事録

**目的**: 会議の決定事項と次のアクションを記録し、参加者・非参加者が後から参照できるようにする

**推奨構成**:
1. 基本情報（日時、参加者、目的）
2. 決定事項（箇条書き、担当者・期限付き）
3. 議論の要点（決定に至った経緯）
4. 次のアクション（Who/What/When）
5. 持ち越し事項

**書き方のポイント**:
- 決定事項を最上部に置く（忙しい人向け）
- 議論の詳細より「何が決まったか」を優先
- アクションには必ず担当者と期限を入れる
- 発言者の名前は必要な場合のみ記載

---

## 企画書・提案書

**目的**: 承認者を説得し、プロジェクトの実行許可を得る

**推奨構成**:
1. 提案の要旨（1段落で結論）
2. 背景・課題
3. 提案内容
4. 期待効果（定量化できるものは数字で）
5. 必要リソース・コスト
6. スケジュール
7. リスクと対策

**書き方のポイント**:
- 結論を先に述べる（忙しい承認者向け）
- 「なぜ今やるのか」を明確にする
- 効果は可能な限り定量化する
- 代替案との比較があると説得力が増す

---

## 報告書

**目的**: 実施した内容と結果を正確に伝える

**推奨構成**:
1. 要約（結論を先に）
2. 背景・目的
3. 実施内容
4. 結果・成果
5. 考察・学び
6. 今後の計画

**書き方のポイント**:
- 事実と解釈を明確に分ける
- 数字やデータを根拠として示す
- 成功だけでなく、課題や失敗も正直に記載する
- 次のアクションにつなげる

---

## 共通の注意事項

### 読者を意識する
- 誰が読むのか（専門家？非専門家？経営層？現場？）
- 何を知りたいのか（詳細？概要？結論だけ？）
- どのくらい時間をかけて読むのか

### 略語・造語のルール
- 初出時は必ず正式名称を併記: CEP（Category Entry Point: カテゴリーエントリーポイント）
- 社内用語は外部読者向けには避けるか、用語集を設ける
- 3文字以上の略語が5個以上出てきたら、冒頭に用語集を設ける

### 構造化のバランス
- 箇条書きは「並列の情報」に使う。すべてを箇条書きにしない
- 太字は本当に強調したい箇所だけ。1セクションに2-3箇所まで
- フレームワーク（GROW, OKR等）は内容に合えば使う。無理に当てはめない
