# 競合調査スキル

このスキルは、PRDや戦略メモを書く際に必要な「競合サービスの仕様・体験の深掘り調査」をユーザーと共創するためのものだ。
**調査を始める前に必ず質問で範囲を確定する**。勝手に探しに行かない。

## 基本原則

1. **Ask First（質問先行）**: 調査に入る前に[Question]/[Answer]形式で対象・観点・出力先を確定させる。曖昧なまま走らない
2. **Deep over Broad（広く浅くより狭く深く）**: デフォルトは3サービスを公式ドキュメント・ヘルプページ・画像まで踏み込んで深掘り。表面的な要約で終わらせない
3. **Self-Contained**: PRDから参照しても単体で読める形式で書く。「詳細はXXを参照」で逃げない。画像リンク・引用・一次ソースURLを本文に埋め込む
4. **Evidence-Based**: 憶測や一般論ではなく、ヘルプページ・公式ドキュメント・スクショ由来の引用を根拠にする。推測する場合は「推測:」と明示する
5. **Subagent-First, No Re-Summarization（サブエージェント主体・再要約禁止）**: 調査は必ずサブエージェント（`Agent` tool）に並列で投げる。サブエージェントの戻り値をメインが要約してはいけない。サブエージェント自身が成果物ファイルを直接書き出し、メインはそのファイルを `Read` して統合レポートを組み立てる。詳細・引用・URLを戻り値経由で受け渡すと情報が痩せる

## ワークフロー

### フェーズ1: 質問（Question）— 調査前に必ず実施

ユーザーからの依頼を受けたら、**最初のターンでは調査に入らず** 以下を[Question]/[Answer]形式で順に確認する。
一度に全部聞かず、2〜3問ずつ小分けにして聞く。

**Q1. プロジェクト文脈**
- どのプロジェクト/PRDの文脈での調査か？（出力先ディレクトリの決定に使う）
- 具体的にPRDのどのセクションで参照される想定か？（例: 「検証セクションの競合調査」「ソリューション設計時のUX参考」）

**Q2. 調査対象領域**
- 何を調べたいか？（例: "X (Twitter) API連携の認可フローとUX"、"Slackのスレッド通知UI"）
- 特に知りたいのは「UI/UXフロー」「API仕様」「機能スコープ」「料金」のどれか？（複数可）

**Q3. 比較対象サービス**
- 調べるサービスは決まっているか？ 決まっていない場合、こちらから候補を3つ提案する
- 「〇〇は必ず含めたい」など必須指定があれば教えてほしい

**Q4. 深掘り観点（PRDで迷っているポイント）**
- 特に詰めたい具体論点は何か？（例: "連携解除時のトークン無効化タイミング"、"エラー時のユーザー通知方法"）
- 知りたいのは「スクショで見たいUI」「ドキュメントの文言」「実装上の制約」のどれか？

**Q5. 出力先・命名**
- 出力先ディレクトリを提案: `projects/{project}/research/YYYY-MM-DD-{topic}.md`
- `{project}` と `{topic}` の値をユーザーに確認する
- プロジェクト名が不明な場合は `references/competitors/YYYY-MM-DD-{topic}.md` にフォールバック

全ての回答が揃ったら、ユーザーに「この範囲で調査開始して良いか？」と最終確認する。

### フェーズ2: 調査計画の提示

調査開始前に、以下を1メッセージでユーザーに提示して承認を得る：

- **対象**: サービスA、B、C
- **観点**: UI（スクショ）/API仕様/機能範囲/料金 など合意した観点
- **一次ソース優先順**: 公式ヘルプセンター → 公式ドキュメント → 公式ブログ → 信頼できる第三者レビュー
- **深掘り度**: 3サービスそれぞれ、画面フロー単位で追う
- **実行方式**: サービスごとに **サブエージェントを並列起動**。各サブエージェントは成果物ファイル（`sources/{service}.md`）に直接書き込む。メインは戻り値を要約せず、ファイルを `Read` して統合する
- **出力構造**:
  ```
  {base_dir}/YYYY-MM-DD-{topic}/
    ├── sources/
    │   ├── {service-a}.md   ← サブエージェントAが直接書く（詳細・引用・画像URL全部入り）
    │   ├── {service-b}.md   ← サブエージェントBが直接書く
    │   └── {service-c}.md   ← サブエージェントCが直接書く
    └── report.md            ← メインが sources/*.md を読んで統合
  ```
  `{base_dir}` は `projects/{project}/research` または `references/competitors`

「この計画で開始します」→ 承認後に調査実行。

### フェーズ3: 調査実行（サブエージェント並列起動）

**CRITICAL: メインは WebFetch/WebSearch を直接叩かない**。必ず `Agent` tool で `subagent_type: "general-purpose"` のサブエージェントをサービスごとに起動し、**1メッセージ内で並列実行**する。

**サブエージェント起動の書き方:**

各サービスにつき1つの Agent 呼び出し。プロンプトには以下を明示する：

1. **調査対象サービスと観点**（フェーズ1で合意したもの）
2. **成果物の書き出し先フルパス**: `{base_dir}/YYYY-MM-DD-{topic}/sources/{service}.md`
3. **書き出しフォーマット**: [references/source-template.md](references/source-template.md) に従え、と指示
4. **深掘り手順**（下記の「サブエージェントに渡す調査手順」をプロンプトに貼る）
5. **戻り値の指示**: 「書き出したファイルパスと、調査中に詰まった未解決項目のみ200字以内で報告せよ。詳細はファイルに全部書け。メインに要約を返す必要はない」
6. **禁則**: 「情報を省略・要約するな。公式ヘルプの原文引用・画像URL・一次ソースURLは必ずそのまま成果物に残せ」

**サブエージェントに渡す調査手順（プロンプトに埋める）:**

```
1. 公式トップ・製品ページを WebFetch で読み、製品の位置づけを把握
2. ヘルプセンターを検索し、対象機能の仕様説明ページを特定。WebFetch で全文を取得
3. 公式ドキュメント / API リファレンスで仕様の裏を取る
4. ヘルプページ内のスクショURLは `![説明](URL)` 形式で成果物に埋め込む
5. 動画・画像でしか分からないUIは、該当セクションURLを記録
6. よくある質問セクションも読む（仕様の行間が出やすい）

記録すべきこと:
- 機能の公式名称（そのまま使う）
- UI/UXフローのステップ by ステップ
- API/技術仕様のキー挙動（OAuthスコープ、トークン寿命、Webhook有無など）
- 料金プランとの関係
- 参照した一次ソースURL（脚注で）

WebFetch/WebSearch は必要なだけ叩いてよい（10〜20回目安）。
```

**メインの動き:**

- サブエージェント起動は並列（1メッセージで複数 Agent 呼び出し）
- 戻ってきたら **戻り値を要約・転記しない**。ユーザーへは「サービスA/B/Cの調査完了、各ファイルに書き出し済み」程度の一言で良い
- 未解決項目が報告されたら、それだけをユーザーに共有して方針確認

### フェーズ4: 統合レポート出力

1. `sources/*.md` を **全て `Read` で読み込む**（要約せず原文を把握）
2. [references/report-template.md](references/report-template.md) に従って `report.md` を書く
3. レポートは比較表・横断的示唆・PRDへの論点整理に専念し、**詳細は `sources/{service}.md` へのリンクで済ませる**（原文の二重管理を避ける）
4. パス: `{base_dir}/YYYY-MM-DD-{topic}/report.md`

ユーザーには「統合レポートは `report.md`、詳細ソースは `sources/` 配下」と案内する。

### フェーズ5: PRDへの反映提案

レポート完成後、ユーザーに以下を提案：

- 「このレポートの『PRDへの示唆』セクションを、PRDの検証セクションに要約して貼りますか？」
- 「特に重要な論点は〇〇です。PRDに反映しましょうか？」

反映は別スキル（`creating-prd`）に渡す前提でOK。このスキルはあくまで「調査成果物を作る」ところまで。

## 重要な注意事項

### 質問フェーズをスキップしない
ユーザーが「〇〇を調べて」と短い指示をくれても、**必ずフェーズ1の質問を行う**。
「とりあえず調べる」のは時間の無駄になる。範囲確定が最も価値を生む。

ただし、ユーザーが明らかに全情報を提示済みの場合（例: 「X, Slack, Discord の API 認可フローを UX 観点で projects/voice/research/ に出力して」）は、Q1-Q5を1メッセージで確認するだけで済ませる。

### 画像・スクショは必ず埋め込む
ユーザー要望の核は「画像やヘルプページを見て深く知りたい」点。
ヘルプページ内のスクショURLは可能な限り本文に `![説明](URL)` で埋める。
画像が取得できない場合は、代わりに該当ページのアンカー付きURLを記録する。

### WebFetch/WebSearch の使い分け
- **WebSearch**: サービス名 + 機能名で最初のヘルプページ/ドキュメントを探すとき
- **WebFetch**: 特定URLの詳細を読むとき（ヘルプページ本文、API仕様書）

ヘルプページは構造化されているので、WebFetch で取得 → プロンプトで「〇〇機能の仕様を抽出」と指示すると効率的。

### 情報の信頼性
- 一次ソース（公式）> 二次ソース（ブログ・レビュー）> 三次ソース（まとめ記事）
- 三次ソースしか見つからない場合は、その旨を本文に明記する
- 推測は必ず「推測:」プレフィックスを付けて、事実と区別する

### プロジェクトパス決定フロー
1. ユーザーが `{project}` を明示 → そのまま使用
2. 明示されていないが現在のディレクトリに `projects/voice/` 等がある → それを提案
3. 全く不明 → `references/competitors/YYYY-MM-DD-{topic}.md` にフォールバック

このリポジトリ（pm-docs）では `projects/` ディレクトリが未作成の可能性もある。その場合は `mkdir -p projects/{project}/research` で作成する。

## 重要な注意事項（追加）

### メインは要約サマリーを出力しない
サブエージェントから戻った情報をメインAgentが文章化して返すのは禁止。詳細が欲しければユーザーは `sources/{service}.md` を開く。メインは「どこに何を書いたか」のナビゲーションと、ファイル横断で見える比較・示唆のみ担当する。

ユーザーへの完了報告例（これ以上書かない）:
> サービスA/B/Cの調査完了。
> - 詳細: `sources/a.md`, `sources/b.md`, `sources/c.md`
> - 統合: `report.md`
> - 未解決: Aのトークン無効化タイミングはヘルプに記載なし

### サブエージェント起動の必須要素
Agent呼び出し時のプロンプトには必ず以下を含める：
- 書き出し先フルパス
- [references/source-template.md](references/source-template.md) 準拠の指示
- 「省略・要約禁止、原文引用・画像URL・一次ソースURLを全部残せ」
- 「戻り値は200字以内、詳細はファイルに書け」

## リソース

### references/report-template.md
メインAgent用の統合レポートテンプレート。比較表・横断示唆・PRDへの論点整理が中心で、詳細は `sources/` へのリンクで済ませる構造。

### references/source-template.md
サブエージェント用のサービス単体深掘りテンプレート。原文引用・画像URL・ステップ詳細・参照ソース一覧を全部残す構造。サブエージェント起動時のプロンプトで参照させる。
