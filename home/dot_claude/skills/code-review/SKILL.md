# Code Review Skill

PR番号またはコード差分に対し、自動でdiffを取得して **変更概要サマリー** と **レビュー指摘** を出力する。

## ⚠️ 重要: このスキルを必ず使用すること

**コードレビューを依頼されたら、必ずこのスキルを起動してください。**

- ❌ **禁止**: 直接`git diff`や`gh pr diff`を実行してレビューを書く
- ✅ **正解**: このスキル（`/code-review`）を使用する

**理由**:
1. **構造化されたレビュー**: 優先度別（P1〜P5）の分類で重大度が明確
2. **具体的な修正案**: P1-P2には必ずコード例を含む修正提案
3. **包括的な分析**: 変更概要（Why/What/Where/How）+ レビュー指摘
4. **一貫性**: レビューフォーマットが統一され、見落としが減る

スキルを使わずに直接レビューすると、上記のメリットが失われます。

## レビュー実行手順

### Step 1: PR情報の取得

PR番号が渡された場合、以下のコマンドで情報を取得:

```bash
# PRの概要・目的を取得
gh pr view <PR番号>

# 差分を取得
gh pr diff <PR番号>

# 変更ファイル一覧
gh pr diff <PR番号> --name-only
```

### Step 2: コンテキスト収集

変更ファイルごとに以下を確認:
- 変更箇所の前後のコードをReadツールで読む
- 関連するテストファイルの有無を確認
- 呼び出し元・呼び出し先の影響範囲を把握

### Step 3: 優先順位に従いレビュー

#### P1: バグ・ロジック破綻（最優先 - マージ即障害リスク）

- エッジケース・null/undefined処理の漏れ
- ループ・条件分岐の誤り
- 非同期処理の順序・競合状態
- データ整合性の破壊（スキーマ不整合など）
- 既存コードへの副作用

#### P2: セキュリティ・パフォーマンス・例外処理

- 入力バリデーションの不備
- 外部サービス呼び出しのエラーハンドリング欠如
- O(N²)や不要なJoin等の計算量問題
- 同期処理すべきでない重い処理
- クレデンシャルのハードコード・露出

#### P3: 仕様との一致

- 入出力が仕様通りか
- PRの目的(Why)とdiff(What)の整合性
- ユースケースを満たすテストの有無
- 想定利用パターンでの誤作動可能性

#### P4: 設計の一貫性（長期保守コスト）

- 責務の分散・重複
- 関数抽出すべき類似ロジック
- 過度な抽象化
- 既存アーキテクチャとの整合

#### P5: 可読性（最低優先）

- 命名の明確さ
- 関数サイズ（1関数1責務）
- コメントの過不足

### Step 4: サマリーレポート出力

```markdown
## 変更概要

**対象**: PR #[番号] - [タイトル]

### 目的（Why）
[PRのタイトル・説明・コミットメッセージから読み取れる変更の意図・背景]

### 主要な変更点（What）
変更ファイルを機能単位でグルーピングして説明:
1. **[機能/コンポーネント名]**
   - `ファイルA.tsx` - ○○を追加
   - `ファイルB.ts` - ××のロジックを変更
2. **[別の機能名]**
   - `ファイルC.ts` - △△を修正

### 影響範囲（Where）
- **画面**: ○○ページ、××ダイアログ（影響なしの場合は「なし」）
- **API**: なし / エンドポイント名
- **DB**: なし / スキーマ変更あり（マイグレーション内容）
- **他サービス連携**: なし / ○○への影響

### 動作の変化（How）
ユーザーや開発者から見た挙動の変化:
- Before: ○○だった
- After: ××になる

---

## レビュー結果

**結論**: [Approve / Request Changes / Comment]

### 指摘事項

#### 🔴 P1: バグ・ロジック破綻
- `file:line` - [指摘内容]
  - 修正案: [具体的なコード例]

#### 🟠 P2: セキュリティ・パフォーマンス
- `file:line` - [指摘内容]

#### 🟡 P3: 仕様との不一致
- `file:line` - [指摘内容]

#### 🔵 P4: 設計
- `file:line` - [指摘内容]

#### ⚪ P5: 可読性
- `file:line` - [指摘内容]

### 良い点
- [ポジティブなフィードバック]

### 総評
[全体的な評価と推奨アクション]
```

## 判断基準

| 状況 | 結論 |
|------|------|
| P1に問題あり | Request Changes |
| P2-P3に重大な問題あり | Request Changes |
| P4-P5のみ指摘 | Comment（ブロックしない） |
| 問題なし | Approve |

## 注意事項

- 指摘がない優先度のセクションは省略可
- P1-P2の指摘には具体的な修正案を提示する
- PRの目的を理解した上でレビューする（過剰な指摘を避ける）
