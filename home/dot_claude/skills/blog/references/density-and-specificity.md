# 密度と具体性のルール

blog.md（AI生成の典型的失敗例）と final.md（著者が手直しして完成させた版）の before/after を並べ、「どういう文章を書くな、どういう文章を書け」を具体例で示す。

Phase 3 のセクション執筆subagent、Phase 4-1 構成レビュー、Phase 4-3 削るパスに渡す。

---

## 大原則

**AIが書きがちな文章（blog型）の特徴**
- 素材の1行を2〜3文に水で薄めて段落にする
- 素材にない情報は一切足さない（結果、著者しか書けない具体が消える）
- 論点を番号付きで展開する（差別化3つ、戻った理由3つ、など）
- 見出しに「PM視点:」「技術視点:」のようなメタラベルを付ける
- 汎用的な決意表明で締める（「打率を上げていきたい」）
- 「〜と思います」「〜と感じています」「ただ」「また」で段落を繋ぎ、長さを稼ぐ

**著者が書きたい文章（final型）の特徴**
- 素材の論点を**畳む**（3つを1文に、2段の理由を1段に）
- 素材にない**実装の中身・固有名詞・リンク**を足す（著者しか書けない具体）
- 見出しにラベルを付けず、内容そのままを短く書く
- 締めは今回の体験から出た具体的な次アクション
- 1段落は1〜3文。接続詞で延ばさない

**判定基準（subagentは出力前に必ずチェック）**
自分の出力を1段落ずつ見て：
- その段落は素材の1行を引き延ばしたものか？ → YES なら削る
- その段落に、著者しか書けない具体（数字、固有名詞、実装の中身、リンク）が1つ以上あるか？ → NO なら足すか削る
- その段落は前の段落と同じ主張を言い換えていないか？ → YES なら統合する

## 実例: blog.md (NG) → final.md (OK)

### 例1: 論点の畳み方

**NG（blog.md）** — 差別化3つを番号付きで展開（4文、約210字）

> 自分なりに考えている差別化の方向性は3つあります。ひとつめは、データを蓄積してパーソナライズすること。テニラボでは過去のメモを横串で分析してパターンを見つけるような使い方ができます。ふたつめは、専用UIを用意すること。メモを入力したら即コーチングが返ってくるワンアクションの体験は、汎用Chatではなかなか実現しにくい。みっつめは、ドメインナレッジの埋め込みです。テニスコーチの思考プロセスをプロンプトに組み込むことで、通常のChatでは得られない回答を返せるようにしています。

**OK（final.md）** — 同じ3論点を1文に畳む（1文、約80字）

> 今回はデータを蓄積してパーソナライズする。専用UIを用意しユーザの負担をさらに下げる。テニスコーチの思考プロセスをプロンプトに組み込み通常のチャットでは得られない回答を返せるようにする、といった工夫をしてみました。

**何が起きているか**
- blog は「ひとつめは〜」「ふたつめは〜」で論点を展開。各論点にさらに説明文を足して段落を作る
- final は3論点を読点で繋いで1文化。「〜といった工夫をしてみました」で丸めて次に進む
- **個人ブログの論点展開は1文で十分なことが多い**。番号付きで展開するかどうかは、その論点が記事の主張の中心かどうかで決める

### 例2: 材料を水で薄めない

**NG（blog.md）** — 戻った理由を2段で展開（2段落、約430字）

> 戻った理由はそれだけではありません。どんどん自分の理解からコードベースが離れていくことが一番の壁でした。Viteのベストプラクティスなどがわからない状態で指示を続けていたので、現状把握のための質問をせざるを得なくなりました。的確な指示を出すには、自分がコードの現在地を把握している必要があります。AIに任せるほどその把握が難しくなるという構造的なジレンマがあったと思います。
>
> フィードバックサイクルの回しづらさも感じました。ローカルストレージやデータの同期周りのエラーは環境差異により再現が出にくく、手元でどれだけ同じ再現ができるかが問題になります。認証やDBの設計、データの同期周りは間違えると大変だし、初回はしっかりレビューしないといけませんでした。こうした領域はAIに任せきりにできない部分です。

**OK（final.md）** — 1段落に圧縮（1段落、約120字）

> また今回の開発ではいくつかフィードバックサイクルの回しづらさも感じました。ローカルストレージやデータの同期周りのエラーは環境差異により再現がしづらく、かなり工夫しないと、AIに任せきりにできなくなってしまうなと感じました。

**何が起きているか**
- blog は「理由その2」を2段落かけて展開。「構造的なジレンマがあったと思います」のような抽象的な総括で締める
- final は「コードベースから自分が離れる」論点を**削除**し、「フィードバックサイクル」論点だけを1段落で済ませる
- **著者が大事だと思う論点だけを残し、material にあった他の論点は思い切って削る**。全部書くと冗長になる

### 例3: 材料にない具体を足す

**NG（blog.md）** — 技術スタックを並べて終わり

> フロントエンドはReact 19 + TypeScript + Vite + Tailwind CSS 4 + shadcn/ui + Zustandという構成です。バックエンドはFastAPI + Python 3.12 + uvで、LLMにはGoogle Gemini API（gemini-3.1-flash-lite-preview）を使っています。認証とデータベースはSupabase、デプロイ先にはexe.devを選びました。PWAにも対応しています。
>
> 開発ツールとしてはClaude Codeを中心に据えていて、カスタムagentsやskillsを組み合わせて使っています。CIはGitHub Actionsです。

**OK（final.md）** — 材料にない「バックエンドがどう動いているか」を1段深く足す

> フロントエンドはReact 19 + TypeScript + Vite + Tailwind CSS 4 + shadcn/ui + Zustandという構成です。
>
> バックエンドはFastAPI + Python 3.12 + uvで、LLMにはGoogle Gemini API（gemini-3.1-flash-lite-preview）を使っています。認証とデータベースはSupabase、デプロイ先にはexe.devを選びました。PWAにも対応しています。
>
> バックエンドではユーザのメモ入力と診断結果をベースにコンテキストを組み立てAIにコーチの役割を持たせて回答をstructured outputで生成しています。
>
> 開発ツールとしてはClaude Codeを使っていてカスタムagentsやskillsを組み合わせて使っています。

**何が起きているか**
- blog は material.md の技術スタックリストを忠実に文章化しただけ
- final は **material にない** 「バックエンドの動き（コンテキスト組み立て → structured output で返す）」を1文足している
- これは**著者が実際に実装したから書ける情報**。Phase 2.5 の再インタビューで拾うべきタイプの情報
- リストだけのセクションは「リストの外に、実装者だから書ける1段深い説明を1〜2文足す」と読み応えが変わる

### 例4: メタラベル見出しを剥がす

**NG（blog.md）** — 見出しで視点を仕切る

```
## PM視点: AIプロダクトで「使い続けてもらう」ことの難しさ
## 技術視点: バイブコーディングの理想と現実
```

**OK（final.md）** — ラベルなし、内容そのまま

```
## AIプロダクトで「使い続けてもらう」ことの難しさ
## AIベースの開発の理想と現実
```

**何が起きているか**
- blog は「今から2つの視点を提示します」というメタ構造を見出しで見せる
- final はメタ構造を消して、連続した振り返りとして読ませる
- **「PM視点:」「技術視点:」「考察:」「まとめ:」のようなラベルは付けない**。見出しは内容そのもので書く
- Phase 3 の subagent はセクション単位で独立に動くため、セクションが自己完結するようにラベルを盛りがち。明示的に禁止する

---

### 例5: 冒頭の接続先

**NG（blog.md）** — 自分の動機からいきなり入る

> AIでアプリを作る体験がしたくて、自分がほしいものを作ってみた
>
> Claude Meet Up Tokyoに参加したり、Boris Tane氏の記事を読んだりしているうちに、自分もAIを使ってゼロから何か作ってみたいという気持ちが強くなっていました。

**OK（final.md）** — 業界潮流から入り、その中に自分を位置づける

> こんにちは、ひぐです。
>
> 最近Claude Meet Up Tokyoに参加したり、Claude Codeの作者のBoris Tane氏の記事を読んだりしている中で、AIをCopilotではなく主とした開発スタイルが台頭していると感じています。
>
> また、それを実現するために、AIがタスクを正確に実行できるような枠組みを整えるハーネスエンジニアリングの記事も増えています。
>
> 普段の仕事でもAIは使っているものの、任せている度合いはまだ低いと感じていて、このような開発スタイルを一度ちゃんと試したく、アプリを作ってみました。

**何が起きているか**
- blog は「自分が作りたかった」という**閉じた動機**から入る。読者は「で？」となる
- final は「業界でこういう潮流がある → 自分もそれを試したくなった → アプリを作った」という**開いた動機**
- 読者が既に知っている（または興味のある）話題に一度接続してから自分の話に降ろす
- **記事の最初の段落は、読者と自分の間の橋を架ける場所**。自分の動機だけで書かない

### 例6: プロダクト紹介の順序

**NG（blog.md）** — 機能紹介型（いきなり「何ができるか」から）

> ## テニラボの紹介: メモするだけでAIコーチが返ってくる
>
> 一言で説明すると、「テニスのコーチングやスクールに行くと自分の気付かないところを教えてくれるが、それを一人でできるようになった」というアプリです。
>
> テニススクールでコーチに見てもらうと、自分では気づけなかったクセや改善点を指摘してもらえます。ただ、レッスンは週1回あるかないか。…

**OK（final.md）** — 因果ストーリー型（課題 → 洞察 → 解決策の順）

> ## テニラボの紹介: メモするだけでAIコーチが返ってくるアプリ
>
> 今回のアプリのテーマは、趣味のテニスにしました。
>
> 自分はこれまでテニスの練習後に上達のためにメモを書いてたのですが、書きっぱなしで振り返らないまま、次の練習でまた同じミスをする、ということを繰り返していました。
>
> 上達が起きるのは、自分では気づけないミスや考え方を他の人に指摘してもらったときだと思っています。コーチに指摘されたり、動画で新しいやり方を見たり。そういうの役割をアプリで補完できないかと考えて、作ってみることにしました。
>
> 一言で説明すると、「テニスのコーチのように自分の気付かないところを教えてくれる」アプリを目指しました。

**何が起きているか**
- blog は「一言で説明 → 機能」の順。読者は「なぜこれが必要なのか」を知らないまま機能を聞かされる
- final は「自分の課題 → 上達の本質への気づき → だからこういうアプリを作った」の順。**読者が機能を聞く前に"なぜ必要か"を理解する**
- material.md に「なぜ作ったか」ブロックがあるなら、**紹介セクションの冒頭に置く**

### 例7: 締め方

**NG（blog.md）** — 汎用的な決意表明

> ## まとめ
>
> 設計方針やアイデア、技術スタックの選定は自分の中に蓄積されていくので、次回以降の開発はさらに速くなると思います。引き続き、自分がほしいものを作りながら打率を上げていきたいです。

**OK（final.md）** — 今回の経験から出た具体的な次アクション

> ## まとめ
>
> アプリ開発に挑戦してみた話をまとめてみました。
>
> 次のアプリを開発するときはAIさんが自律的に稼働できるようにさらに環境を整えて再挑戦したいと思います！
>
> では〜

**何が起きているか**
- blog は「打率を上げていきたい」という**どんな記事にも使える決意表明**
- final は「今回ハーネスを整備する余裕がなかった」という記事本文の振り返りを踏まえて「**次はAIが自律的に稼働できる環境を整える**」と具体宣言
- **締めは記事本文の論点と接続している必要がある**。汎用決意表明は禁止

## 判定チェックリスト（subagentが出力前に自分に聞く）

自分の書いた段落・セクションを以下でチェック：

| No | チェック項目 | NG なら |
|----|-------------|---------|
| 1 | この段落は素材の1行を引き延ばしただけか | 元の1行に戻すか削る |
| 2 | 材料にない具体（数字・固有名詞・実装の中身・リンク）を1つ以上含むか | Phase 2.5 の「追加素材」を使って足す。無ければ著者に聞く |
| 3 | 前の段落と同じ主張を言い換えていないか | 統合する |
| 4 | 論点を番号付きで展開しているが、1文で流した方が軽くないか | 1文に畳む |
| 5 | 見出しに「〜視点:」「〜考察:」のようなメタラベルを付けていないか | 外す |
| 6 | 冒頭段落が、読者が既に知っている話題から入っているか | 業界の話題・読者の困りごとから入り直す |
| 7 | プロダクト紹介が「なぜ必要か → 何ができるか」の順になっているか | 順序を入れ替える |
| 8 | 締めが記事本文と接続した具体的な次アクションか | 汎用決意表明なら書き直す |
| 9 | 「〜と思います」「〜と感じています」が1段落に2回以上出ていないか | 1回に絞る |
| 10 | 接続詞（「ただ」「また」「そして」「とはいえ」）で無理に段落を延ばしていないか | 段落を分けるか、接続詞を削る |

**最終判定**: 書き終えたセクション全体を見て、このreferenceの「NG（blog.md）」側と「OK（final.md）」側のどちらに近いか、自分で1文で判定する。NG側に寄っていたらもう一度書き直す。
