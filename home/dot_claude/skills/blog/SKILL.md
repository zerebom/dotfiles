# ブログ執筆スキル

状態管理型のブログ執筆スキル。`blog/wip/{topic}/` にファイルを段階的に作成し、ファイルの有無でフェーズを判定する。

## 起動方法

```
/blog              → 進行中のプロジェクトがあれば続きから。なければ新規開始
/blog new {topic}  → 新規プロジェクト開始
/blog status       → 現在の状態を表示
```

## コンテキスト分離の原則

AIは自身の出力を蓄積するほど同じパターンを再生産する。このスキルでは以下の原則でAI臭を防ぐ。

1. **書くagentとレビューするagentは別コンテキスト** — subagentを使い分ける
2. **セクション執筆agentには他セクションのAI出力を見せない** — 人間の生素材 + アウトラインだけ渡す
3. **人間の言葉を最上位ソースとする** — material.md の原文を常に参照可能にする

## フェーズ判定

`blog/wip/{topic}/` 内のファイル存在で現在フェーズを判定する。

| ファイル | 存在する | フェーズ |
|---------|---------|---------|
| (なし) | — | Phase 0: 素材投入を促す |
| material-raw.md | あり | Phase 1: 膨らましを続ける |
| material.md | あり | Phase 2: 構成案を提示 |
| outline.md | あり | Phase 2.5: 構成に沿った再インタビュー |
| material-v2.md | あり | Phase 3: セクション執筆 |
| draft.md | あり | Phase 4: 仕上げ |
| blog.md | あり | 完了: `blog/entries/` への配置を提案 |

**再開時**: `/blog` が呼ばれたら `blog/wip/` を確認。進行中プロジェクトがあればフェーズを判定して続きから開始。複数あればどれを続けるか聞く。

---

## Phase 0: 素材投入

ユーザーから生の素材を受け取る。

**やること**:
1. トピックを確認し `blog/wip/{topic}/` ディレクトリを作成
2. ユーザーに素材投入を促す
   - 「メモ、箇条書き、音声書き起こし、リンク集、何でもOKです。考えていることをそのまま貼ってください」
3. 受け取った素材を `material-raw.md` にそのまま保存（編集しない）

**出力**: `material-raw.md`

**ゲート**: 「素材を受け取りました。膨らましに進みますか？」

---

## Phase 1: 膨らまし

素材を対話で膨らます。メイン会話で実施（subagent不要）。

**やること**:
1. `material-raw.md` を読み、素材の量と質を把握
2. 以下の観点で質問を投げる（一度に3-4問。ユーザーが答えやすいように具体的に）:
   - **読者**: 誰に向けて書く？その人は何を知りたい？
   - **動機**: なぜこれを書こうと思った？
   - **具体例**: エピソード、数字、before/after はある？
   - **意外性**: 読者が「へえ」と思うポイントは？
   - **学び**: 書き手自身が得た気づきは？
3. ユーザーの回答をそのまま（AI要約せず）`material.md` に構造化して保存
   - セクションごとにユーザーの原文を引用する形で整理
   - AI自身の補足は `<!-- AI補足: ... -->` コメントで明示的に分離

**出力**: `material.md`

**ゲート**: 「素材はこれで十分ですか？追加したいことがあれば続けます。構成に進みますか？」

---

## Phase 2: 構成決定

構成案を提示し、ユーザーに選んでもらう。メイン会話で実施。

**やること**:
1. `material.md` を読み、構成案を2-3パターン提示
   - 各パターンにタイトル案 + セクション構成 + 各セクションの1行キーメッセージを含める
   - パターン間の違いを明示（例: 「Aは時系列、Bは問題解決型」）
2. ユーザーが選択・修正したら `outline.md` に保存

**outline.md のフォーマット**:
```markdown
# {仮タイトル}

## メタ情報
- 読者: {誰}
- 目的: {読者に何を持ち帰ってほしいか}
- 想定文字数: {目安}

## 構成

### 1. {セクション名}
- キーメッセージ: {このセクションで伝えたいこと1行}
- 素材: {material.md のどの部分を使うか}

### 2. {セクション名}
...
```

**出力**: `outline.md`

**ゲート**: 「この構成で再インタビューに進みますか？」

---

## Phase 2.5: 構成に沿った再インタビュー

**なぜこのフェーズが必要か**

Phase 1 の material.md は「考えていることを全部出してもらう」段階の素材で、構成が決まる前に作られている。このまま Phase 3 で書き始めると、subagent は material を忠実に文章化するだけなので、以下の2つが必ず起きる：

- **スカスカで冗長**: material の1行を引き延ばして段落にする。書き手が実際に手を動かして得た具体（実装の中身、失敗した瞬間、数字、固有名詞）は material にないので拾えない。結果、一般論を水で薄めた段落が並ぶ
- **冗長だが深まらない**: material にある論点を全部展開するので文字数は増えるが、書き手しか書けない情報は増えない

Phase 2.5 では、**構成が決まった今の状態で、もう一度インタビューする**。各セクションに対して「材料だけで書けるか、書けないなら何を足すか」を著者に確認する。

**やること**

1. `outline.md` のセクション一覧を取得
2. 各セクションについて、メイン会話で以下を順番に聞く（1セクションずつ。まとめて聞かない）:

   **(a) 具体の掘り起こし**
   「このセクションで、material.md に書いていないけど、実際に手を動かしたからこそ書ける具体はありますか？たとえば：
   - 実装・設計の中身（どういう仕組みで動いているか）
   - 失敗した瞬間・詰まった瞬間の固有の状況
   - 数字（時間、回数、金額、サイズ）
   - 固有名詞（ツール名、記事名、人名、ライブラリ名）
   - 引用したい外部ソース（自分の過去記事、参考にした記事、書籍）
   思いつくもの全部で OK です」

   **(b) 分量の決定**
   「このセクション、おおよそ何段落くらいで書きたいですか？1〜2段落でさらっと / 3〜5段落でしっかり / それ以上で深掘り、のどれですか」

   **(c) 削る論点の確認**
   「material.md の中で、このセクションで**使わない / 1文だけ触れる / 削る**ものはありますか？全部展開すると冗長になるので先に決めておきたいです」

3. 回答を `material-v2.md` に構造化して保存
   - outline の各セクション見出しの下に、material.md の該当部分 + Phase 2.5 で追加された情報をまとめる
   - セクションごとに「目安分量」「削る論点」を明記
   - 追加情報の出典が不明なもの（URL、書籍名など）は `要確認` タグを付ける

**material-v2.md のフォーマット**:
```markdown
# セクション別素材（Phase 2.5 再インタビュー版）

## 1. {セクション名}
- 目安分量: {1-2段落 / 3-5段落 / 6段落以上}
- 削る/流す論点: {material.md のどこを使わないか}

### 使う素材（material.md から）
> {引用}

### 追加素材（再インタビューで出てきた具体）
- 実装の中身: {内容}
- 固有名詞・リンク: {内容}
- 数字: {内容}

## 2. {セクション名}
...
```

**出力**: `material-v2.md`

**ゲート**: 「全セクション分の再インタビューが終わりました。これで執筆に進みますか？」

---

## Phase 3: セクション単位の執筆

**ここが品質の要。セクションごとにsubagentを起動し、コンテキスト汚染を防ぐ。**

**やること**:
1. `outline.md` からセクション一覧を取得
2. セクションごとに以下を繰り返す:
   a. **subagent（general-purpose）を起動** し、以下のプロンプトを渡す:

   ```
   あなたはブログのゴーストライター。著者の言葉と文体を忠実に再現する。

   ## 文体ルール
   {references/writing-style.md の内容}

   ## 密度と具体性のルール（最重要）
   {references/density-and-specificity.md の内容}
   → このセクションは「スカスカで冗長」(NG側) ではなく「畳んで具体を足す」(OK側) を目指す。
     references の before/after を見て、自分の出力がどちら寄りか常に判定すること。

   ## このセクションのアウトライン
   {outline.md から該当セクションのみ抜粋}

   ## 素材（Phase 2.5 再インタビュー済み）
   {material-v2.md から該当セクションの全項目（使う素材 + 追加素材 + 目安分量 + 削る論点）}

   ## 制約
   - 素材にない情報を捏造しない。material-v2.md の「追加素材」は捏造ではなく著者の発話として扱う
   - material-v2.md の「削る/流す論点」は展開しない（1文で触れるか、削る）
   - 「目安分量」を超えない。超えそうなら論点を畳む
   - 修飾語は素材にあるものだけ使う
   - 以下の表現は禁止: 「〜と言えるでしょう」「〜ではないでしょうか」「非常に」「極めて」
   - 箇条書きの乱用禁止（素材が地の文なら地の文で書く）
   - 同一の概念には同じ表現を一貫して使う
   - 見出しに「PM視点:」「技術視点:」のようなメタラベルを付けない（references/density-and-specificity.md の「見出し」節参照）

   ## 出力後の自己レビュー（必須）
   出力する前に、自分で書いた文章を以下でチェックし、引っかかったら書き直す：
   1. material-v2.md の1行を2〜3文に水増ししていないか？（水増しなら元の1行に戻すか、削る）
   2. material-v2.md の「追加素材」を全部使ったか？使っていない具体があれば足す
   3. 同じ主張を言い換えて2回書いていないか？
   4. 「目安分量」を超えていないか？超えていたら削る
   5. 最終出力が references/density-and-specificity.md の OK側（final型）に近いか、NG側（blog型）に近いか？NG側ならもう一度書き直す

   このセクションの下書きをMarkdownで出力してください。自己レビューで何を削ったか・何を残したかを出力末尾に `<!-- self-review: ... -->` で付けてください。
   ```

   b. subagentの出力をメイン会話に表示（`<!-- self-review -->` コメントも表示）
   c. ユーザーがレビュー・修正指示
   d. 修正が必要なら新しいsubagentで修正（前のsubagentの出力は「修正対象テキスト」としてのみ渡す）
   e. **承認されたら即座に `draft.md` に追記保存**し、次のセクションへ（セッション中断に備え、確定分を都度ファイルに残す。self-reviewコメントは draft.md には残さない）

3. 全セクション完了後、`draft.md` の内容を最終確認

**出力**: `draft.md`（セクション承認のたびに追記。全セクション完了時には既に統合済み）

**ゲート**: セクションごとに「この内容でOKですか？」、全体統合後に「仕上げに進みますか？」

---

## Phase 4: 仕上げ

レビュー・校正・トリミング。レビューはsubagentで実施。

**やること**:

### 4-1. 全体構成レビュー（subagent、最初に実施）

**セクション単位では検出できない問題を、全体を通しで読むことだけで見つける。**

subagent（general-purpose）を起動し、`draft.md` 全体 + `outline.md` + `material-v2.md` + [references/density-and-specificity.md](references/density-and-specificity.md) を渡す。プロンプト:

```
あなたはブログ編集者。draft.md を「1人の読者として通しで読んで」、以下の観点だけを見る。
文の校正や誤字は見ない（それは別パスでやる）。

チェック観点:
1. 書き出しの段落が、読者を記事に引き込む接続先になっているか
   （業界の話題 / 個人の動機 / 読者の困りごと のいずれかから開いているか。
    いきなり自分の小さな動機だけで始まっていないか）
2. 見出しに「PM視点:」「技術視点:」のような**メタラベル**が付いていないか
   （付いていたら、ラベルを剥がした案を出す）
3. 同じ主張・論点が複数セクションで重複していないか
   （重複していたら、どちらを残すか提案）
4. セクション間の分量バランスが outline.md / material-v2.md の「目安分量」通りか
   （外れていたら、膨らんだセクションのどこを削るか提案）
5. 材料の1行を水で薄めて段落にしている箇所がないか
   （references/density-and-specificity.md の「スカスカで冗長」型の例を参照し、
    該当する段落を指摘）
6. 締めの段落が、今回の体験から出た具体的な次アクションになっているか
   （「〜していきたいです」だけの汎用決意なら、具体性が足りないと指摘）
7. references/density-and-specificity.md の OK側（final型）と NG側（blog型）の
   どちらにこの記事は近いか。NG側に寄っている箇所を指摘

出力フォーマット:
## 全体構成レビュー
### 1. 書き出し: {OK or 問題点}
### 2. 見出し: {メタラベルの有無と剥がし案}
### 3. 重複: {重複の有無と統合案}
### 4. 分量バランス: {外れているセクション名と削る候補}
### 5. 水増し箇所: {行番号と該当段落、削り方}
### 6. 締め: {OK or 具体化案}
### 7. 総評: OK側 / NG側 / 中間 のどれに近いか、1文で
```

結果を `reviews/structure.md` に保存し、メイン会話で指摘を提示。ユーザーが修正判断する。

### 4-2. AI臭チェック（subagent）
subagent（strict-writing-reviewer）を起動し、`draft.md` を渡す。
チェック観点は [references/ai-smell-checklist.md](references/ai-smell-checklist.md) を参照。

結果を `reviews/ai-smell.md` に保存し、メイン会話で指摘を提示。

### 4-3. 削るパス（subagent）

**「AI臭」とは別に、冗長さだけを専門に見る。**

subagent（general-purpose）を起動し、`draft.md` + [references/density-and-specificity.md](references/density-and-specificity.md) を渡す。プロンプト:

```
あなたは編集者。draft.md の冗長な箇所だけを見る。AI臭や誤字は見ない。
references/density-and-specificity.md の「畳む型」を参照して、以下を全部やる：

1. 同じ主張を言い換えて2回以上書いている箇所 → 1回に絞る案を出す
2. 材料の1行を2〜3文に引き延ばしている箇所 → 元の1行に戻すか、削る案を出す
3. 接続詞（「ただ」「また」「そして」「とはいえ」）で無理に段落を延ばしている箇所
4. 1文で済む列挙を3文で書いている箇所 → 1文に畳む案を出す
5. 「〜と思います」「〜と感じています」が1段落に2回以上出ている箇所 → 1回に絞る
6. 論点を番号付きリストで展開しているが、本文1文で流した方が軽い箇所

出力は「削り前 → 削り後」のdiff形式で行番号付きで列挙。
文字数の増減目安も書く（例: -180字）。
```

結果を `reviews/trim.md` に保存し、メイン会話で提示。

### 4-4. 校正（subagent）
別のsubagent（general-purpose）を起動し、`draft.md` + [references/proofreading-rules.md](references/proofreading-rules.md) を渡す。

結果を `reviews/proofread.md` に保存し、メイン会話で指摘を提示。

### 4-5. ユーザー修正判断と適用
4-1〜4-4 のレビュー結果を見てユーザーが修正箇所を判断。AIが修正を実施。
適用順は「構成レビュー（4-1）→ 削るパス（4-3）→ AI臭（4-2）→ 校正（4-4）」。構成から文へ、大きい単位から小さい単位へ降りる。

### 4-6. 補完提案
- 追加すべきリンク・参考情報
- 画像・図が必要な箇所の提案
- コード例の追加候補

### 4-7. 完成
`blog.md` として保存。

**出力**: `blog.md`

**ゲート**: 「完成しました。`blog/entries/` に配置しますか？」

---

## 完了処理

`blog.md` が完成したら:
1. `blog/entries/YYYYMMDD_{topic}/blog.md` にコピー
2. `blog/wip/{topic}/` はアーカイブとして残す（作業過程の記録）

---

## 重要なルール

### 対話ルール
- フェーズ間の遷移は必ずユーザーに確認する。勝手に進めない
- セクション執筆中も1セクションごとにレビューを挟む。一括生成しない
- どのフェーズからでも前のフェーズに戻れる（「素材を追加したい」→ Phase 1 に戻る）

### AI臭防止ルール
- `material.md` の人間の言葉が最上位ソース。AIの要約で上書きしない
- セクション執筆subagentには他セクションのAI出力を渡さない
- レビューsubagentには執筆過程の会話を渡さない
- 以下の表現は全フェーズで禁止:
  - 「〜と言えるでしょう」「〜ではないでしょうか」
  - 「非常に」「極めて」「まさに」の乱用
  - 太字の過剰使用（本当に強調したい箇所のみ）
  - 箇条書きの乱用（地の文で書けるなら地の文）

### ファイル管理ルール
- 作業ファイルは `blog/wip/{topic}/` に置く
- 完成記事は `blog/entries/YYYYMMDD_{topic}/` に配置
- `blog/drafts/` はスキル管理外の単発下書き用（混ぜない）

## リソース

### references/writing-style.md
著者の文体特徴。Phase 3 のセクション執筆subagentに渡す。

### references/density-and-specificity.md
密度と具体性のルール。**最重要**。blog.md（NG型、AI生成の実例）と final.md（OK型、著者が手直しした実例）の before/after を並べて、「スカスカで冗長」と「畳んで具体を足す」の差を具体例で示す。Phase 3 のセクション執筆subagentと、Phase 4-1 構成レビューと、Phase 4-3 削るパスに渡す。

### references/ai-smell-checklist.md
AI臭チェック観点。Phase 4-2 のレビューsubagentに渡す。

### references/proofreading-rules.md
校正ルール。Phase 4-4 の校正subagentに渡す。
