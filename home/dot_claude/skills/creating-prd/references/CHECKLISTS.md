# レビューチェックリスト

Reviewフェーズでは、以下のペルソナになりきってドラフトを批判的にチェックしてください。
各観点から抜け漏れや矛盾を指摘し、ユーザーに改善提案を行います。

---

## エンジニアリングマネージャー視点

エンジニアリングマネージャーとして、技術的実現性と保守性の観点からレビューします。

### チェック項目

- [ ] **エッジケース**: ネットワークエラー、空データ、最大値超過時の挙動は定義されているか？
- [ ] **技術的実現性**: 既存のシステムアーキテクチャやDB構造と矛盾していないか？（セクション5.4 現状と依存関係を参照）
- [ ] **マイグレーション**: 既存データへの影響や移行手順は考慮されているか？
- [ ] **拡張性**: 将来の機能追加を阻害しない設計か？
- [ ] **パフォーマンス**: 想定される負荷やデータ量に対して、実現可能な性能要件か？
- [ ] **セキュリティ**: データの取り扱いやアクセス制御について適切に定義されているか？
- [ ] **依存関係**: セクション5.4の依存関係は網羅されているか？プラットフォーム対応は正しいか？

### 指摘例

- 「ユーザーシナリオ（セクション5.2）のMust #3に、エラー時のハンドリングが定義されていません。受け入れ基準にエラーケースを追加しますか？」
- 「セクション5.4で管理画面V2が対象外となっていますが、セクション3.1のペルソナの利用シーンと矛盾していませんか？」

## シニアプロダクトマネージャー視点

シニアPMとして、ビジネス価値とユーザー体験の観点からレビューします。

### チェック項目

- [ ] **WHYの明確さ**: セクション1-3（サマリー、背景、課題と機会）で「なぜやるのか」が明確か？
- [ ] **JTBD とゴールのつながり**: セクション3.2のJTBDとセクション5.1のゴールが対応しているか？
- [ ] **ペイン/ゲインとゴールの整合**: すべてのゴールがペインまたはゲインに紐付いているか？
- [ ] **検証の十分さ**: セクション4（検証）に具体的な顧客名やエビデンスがあるか？裏付けは十分か？
- [ ] **MoSCoW優先度**: Must要件が多すぎないか？（2-5個が目安）優先度判断がユーザー価値に基づいているか？
- [ ] **成功指標の計測可能性**: セクション6のアウトカム指標は実際に計測可能か？測定方法は明確か？
- [ ] **ユーザー体験**: エラー時のフィードバックなど、Un-happy pathの体験は考慮されているか？

### 指摘例

- 「セクション3.3のペイン2に対応するゴールがセクション5.1にありません。ゴールに追加するか、ノンゴールとして明示しますか？」
- 「セクション4.2の需要に具体的な顧客名が1社しかありません。追加のヒアリングや営業チームへの確認は可能ですか？」
- 「セクション6.1のアウトカム指標に『ユーザー満足度向上』とありますが、具体的な測定方法が未定義です。どう測定しますか？」

## カスタマーサクセスマネージャー視点

CSMとして、顧客への説明のしやすさと実運用の観点からレビューします。

### チェック項目

- [ ] **説明可能性**: セクション3.1のペルソナに対して、この機能をどう説明するか明確か？
- [ ] **初期セットアップ**: ユーザーが初めて使う際のオンボーディング体験は考慮されているか？
- [ ] **トラブルシューティング**: ユーザーが困った時のサポート方法は明確か？
- [ ] **既存ワークフローへの影響**: セクション3.2のJTBDの既存の達成方法に悪影響を与えないか？
- [ ] **顧客フィードバック**: セクション4.2のインタビューメモは最新か？追加ヒアリングは必要か？

### 指摘例

- 「セクション4.2の具体的な顧客リストに挙がっている企業に対して、具体的にどのようなデモや資料を用意しますか？」
- 「セクション3.1のペルソナの『ITリテラシー』が高い前提になっていますが、実際の顧客層にはIT非専門の方も多いのでは？」

---

## QAエンジニア視点

QAエンジニアとして、テスト可能性と品質の観点からレビューします。

### チェック項目

- [ ] **受け入れ基準**: セクション5.2のMust/Should/Couldの各ユーザーストーリーに、テスト可能な受け入れ基準があるか？
- [ ] **境界値**: 制約事項（セクション7）で定義された上限値の境界でのテストケースは想定されているか？
- [ ] **異常系**: 正常系だけでなく、異常系・例外系のシナリオは網羅されているか？
- [ ] **一貫性**: PRD全体で用語やMoSCoW優先度に一貫性があるか？
- [ ] **テスト可能性**: 各要件は客観的にテスト可能な形で記述されているか？

### 指摘例

- 「セクション5.2のMust #2の受け入れ基準が『使いやすいこと』となっていますが、テスト可能な基準ではありません。具体的な条件を定義できますか？」
- 「セクション7の制約事項に上限値が記載されていますが、その上限を超えた場合のユーザーストーリーがセクション5.2にありません。」

---

## 全体整合性チェック

すべての視点を踏まえて、PRD全体の整合性を確認します。

### チェック項目

- [ ] **縦の整合性**: サマリー → 背景 → 課題と機会 → 検証 → ソリューション → 成功指標 の流れに論理的なつながりがあるか？
- [ ] **横の整合性**: KPI整合性（4.1）とアウトカム指標（6.1）は対応しているか？ペルソナ（3.1）とユーザーストーリー（5.2）は整合しているか？
- [ ] **JTBD→ゴール→ユーザーストーリーの一貫性**: 各JTBDに対応するゴールがあり、各ゴールに対応するユーザーストーリーがあるか？
- [ ] **ペイン/ゲイン→ゴール/ノンゴールの対応**: すべてのペインとゲインがゴールまたはノンゴールでカバーされているか？
- [ ] **抜け漏れ**: すべてのセクションが適切に埋められているか？「TODO」や「TBD」が残っていないか？
- [ ] **MoSCoW優先度の一貫性**: ユーザーストーリーの優先度が妥当か？Mustが多すぎないか？
- [ ] **オープンクエスチョン**: セクション7の未解決事項が放置されていないか？

### 指摘例

- 「セクション3.2のJTBD #3に対応するユーザーストーリーがセクション5.2に見当たりません。Won'tとして記録するか、ユーザーストーリーを追加する必要があります。」
- 「セクション1のサマリーで述べた『〇〇の工数削減』がセクション6.1のアウトカム指標に含まれていません。測定指標を追加しますか？」
