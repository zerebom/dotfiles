# PRD共創スキル

このスキルは、ユーザーの「思考のパートナー」としてPRDを作成するためのガイドラインです。
一度に完成品を出力しようとせず、**「提案 → ユーザーレビュー → 修正 → 次へ」** というサイクルを回してください。

## 基本原則

1. **小分けにする (Small Batches)**: 全文を一気に出力しないでください。セクションごと、あるいはトピックごとに作成し、ユーザーの確認を求めてください。
2. **確認する (Ask, Don't Assume)**: メモにない情報は勝手に捏造せず、「ここはどのように定義しますか？」とユーザーに問いかけてください。
3. **ファイルに残す (File-First)**: 議論して合意した内容は、チャットの中だけで終わらせず、必ずローカルのMarkdownファイル（例: `prd.md`）に反映・更新してください。
4. **行数上限を守る (Keep it Readable)**: 本文は全体で 200-350 行、上限 500 行。人が通読できる分量に収める。上限を超えそうになったら、本文を削るか付録（同一ファイル末尾）に退避する。外部ファイル分割はしない（self-containedルールのため）。
5. **冗長な書き方を避ける (No Redundancy)**: Pain/Gain/Goal で同じ内容を3回書かない。要件はユーザーストーリー形式ではなく短文タスク記述で書く。表は2列以上の比較・マトリクスに限定する。詳細は [TEMPLATES.md](references/TEMPLATES.md) の「冗長化を招く書き方」参照。

## ワークフロー

以下の5つのフェーズを意識して進行しますが、ユーザーの割り込みや手戻りを常に歓迎してください。

### フェーズ1: WHYの確認（サマリー〜課題と機会）

まず、「なぜこのプロジェクトをやるのか」を明確にします。

**1-1. サマリーの作成:**
- 入力されたメモを読み込みます
- [TEMPLATES.md](references/TEMPLATES.md) のセクション1を参考に、2-3文のサマリーを作成します
- 「誰の」「何の課題を」「どう解決するか」を一目で伝える文にします
- **アクション**: 「このサマリーで方向性は合っていますか？」と確認します

**1-2. 背景と経緯の整理:**
- プロジェクトの起点（どこから出てきたか）を確認します
- 経緯（どのような流れで立ち上がったか）を整理します
- なぜ今取り組む必要があるかを明確にします
- **アクション**: 「背景の記述で補足や修正はありますか？」と確認します

**1-3. 課題と機会の定義:**
- **ターゲットペルソナ**: 具体的な属性・利用シーンを定義します
- **Jobs-to-be-done**: ペルソナが達成したいジョブを3-5個リストアップします
- **ペイン**: 各ジョブを達成する際の現在の問題を具体的に記述します
- **ゲイン**: 期待しているがまだ得られていない価値を記述します
- **アクション**: 「この課題定義で進めて良いですか？足りない観点はありますか？」と確認します

### フェーズ2: 検証（需要と市場の裏付け）

課題が正しいことを裏付けるエビデンスを整理します。

**2-1. KPI整合性の確認:**
- 今期のプロダクトKPIや会社ビジョンとの関連を整理します
- 直接的な寄与か間接的な寄与かを明確にします
- 箇条書きで記載します（1-2列の情報は表にしない）

**2-2. 需要の整理:**
- 具体的な顧客名（by name）でニーズを記載します
- インタビューメモや顧客との会話へのリンクを整理します
- **アクション**: 「具体的な顧客名をもう少し挙げられますか？」と確認します

**2-3. 競合調査・市場トレンドの整理:**
- 競合他社のソリューションと比較します
- 関連する市場・業界トレンドを記載します
- **アクション**: 「十分な裏付けがありますか？足りない観点はありますか？」と確認します

### フェーズ3: ソリューション設計

何を作り、何を作らないかを明確にします。

**3-1. ゴールとノンゴールの定義:**
- ゴールはフェーズ1で定義したペインの解消・ゲインの創出に対応させます
- ノンゴールは明示的にスコープ外とする内容を記載します（理由も添える）
- **アクション**: 「このスコープで進めて良いですか？」と確認します

**3-2. MoSCoW優先度での要件整理:**
- Jobs-to-be-doneに基づき、要件をMoSCoW優先度で分類します:
  - **Must（必須）**: これがないとプロジェクトの価値が成立しない（2-5個）
  - **Should（推奨）**: ユーザー体験を大きく向上させる。ないと強い不満が出る（2-4個）
  - **Could（あると良い）**: 付加価値だが、なくても許容される（0-3個）
  - **Won't（今回対象外）**: 価値はあるが今回は実装しない
- **要件は短文タスク記述で書く**: 1項目 1-2 行の「〇〇できる」形式。「〜として〜したい、なぜなら〜」のユーザーストーリー形式は使わない（冗長になり、セクション3と内容が重複するため）
- **受け入れ基準はPRDに書かない**: Linear Issue 側で詳細化する
- **箇条書きで書く**: 表は使わない
- **アクション**: 「この要件の優先度と内容で進めて良いですか？」と確認します

**3-3. デザインコンセプト・依存関係の整理:**
- UX/UIアプローチの概要を記述します
- 影響を受けるシステム・依存関係を整理します
- プラットフォーム対応状況（コミュニティ ブラウザ/アプリ、管理画面 V1/V2 の対象・対象外）を明記します

### フェーズ4: 成功指標とリスク

プロジェクトの成功をどう測るか、どんなリスクがあるかを明確にします。

**4-1. アウトカム指標:**
- プロダクト指標の改善目標を設定します
- 「[指標名]: [現状値] → [目標値]（測定方法: [方法]）」の箇条書き形式で記載します
- フェーズ2で確認したKPIとの対応関係を明記します

**4-2. アウトプット指標:**
- 具体的なデリバラブルと完了の定義を記載します
- どのアウトカム指標に寄与するかを紐付けます

**4-3. オープンクエスチョン・リスク・制約事項の洗い出し:**
- 未解決の疑問点を箇条書きで記載します
- 想定されるリスクを記載します
- 技術的・ビジネス的な制約事項を記載します
- **アクション**: 「最終確認として、抜け漏れはありますか？」と確認します

### フェーズ5: レビュー

PRD全体の品質を確認します。

**5-1. 多角的レビュー:**
- [CHECKLISTS.md](references/CHECKLISTS.md) を使用して、抜け漏れや矛盾を指摘します
- **アクション**: 「この観点で気になる点がありますが、どうしますか？」と提案します
- ユーザーの承認を得てから更新します

**5-2. 一貫性チェック:**
- セクション間の整合性を確認します:
  - サマリーとゴールの対応
  - ペイン/ゲインとゴール/ノンゴールの対応
  - JTBDとユーザーストーリーの対応
  - KPI整合性とアウトカム指標の対応
  - MoSCoW優先度の一貫性

## 重要な注意事項

### PRDテンプレートの各セクションについて

このスキルが対応するPRDテンプレートは、以下の7セクションで構成されています：

1. **サマリー**: プロジェクト全体を2-3文で説明
   - 「誰の・何の課題を・どう解決するか」を一目で伝える

2. **背景と経緯**: プロジェクトの出発点と今取り組む理由
   - 起点、経緯、なぜ今か

3. **課題と機会**: ターゲットの課題と期待する価値
   - ペルソナ、Jobs-to-be-done、ペイン、ゲイン

4. **検証**: 需要と市場の裏付け
   - KPI整合性、具体的な顧客、インタビュー、競合調査、市場トレンド

5. **ソリューション**: 何を作り、何を作らないか
   - ゴール/ノンゴール、ユーザーシナリオ（MoSCoW優先度）、デザイン、依存関係

6. **成功指標**: プロジェクトの成功をどう測るか
   - アウトカム指標（プロダクト指標の改善）、アウトプット指標（デリバラブル）

7. **オープンクエスチョン・リスク・制約事項**: 未解決の課題とリスク
   - オープンクエスチョン、リスク、制約事項

### セクション執筆時の重要なポイント

- **行数上限を常に意識する**:
  - 本文は全体 200-350 行、上限 500 行
  - セクションごとの目安: 1.サマリー 3-5行 / 2.背景 10-20行 / 3.課題 30-60行 / 4.検証 30-50行 / 5.ソリューション 80-150行 / 6.指標 10-20行 / 7.オープン 10-30行
  - 超過時は本文を削るか付録（同一ファイル末尾）に退避。外部ファイル分割はしない

- **冗長化を招く書き方を避ける**:
  - **3回言い換え禁止**: Pain → Gain → Goal で同じ内容を3回書かない。Pain/Gain に P1, G1 と番号を振り、Goal では `(→ P1, G2)` と参照する
  - **ユーザーストーリー形式を使わない**: 「〇〇として〜したい、なぜなら〜」は冗長。要件は「〇〇できる」の短文1-2行で書く
  - **表は2列以上の比較・マトリクスに限定**: 1-2列の情報（KPI一覧、顧客リスト、成功指標等）は箇条書きで書く
  - **JSON・スキーマ・長いコードブロックは付録へ**: 本文には設計判断の結論だけ書く

- **WHYを先に明確化する**:
  - セクション1-3（サマリー、背景、課題と機会）でWHYを固めてからソリューションに進む
  - WHYが曖昧なままソリューションを書き始めない

- **MoSCoW優先度の運用**:
  - **Must（必須）**: これがないとプロジェクトの価値が成立しない（2-5個に絞る）
  - **Should（推奨）**: ないと強い不満が出る（2-4個）
  - **Could（あると良い）**: なくても許容される（0-3個）
  - **Won't（今回対象外）**: 今回は実装しない（将来の検討材料として記録）
  - 優先度は工数ではなく、ユーザー価値で判断する

- **ペイン/ゲインとゴールの対応（重要）**:
  - セクション3（課題と機会）のペインとゲインは、セクション5.1（ゴールとノンゴール）と直接対応する
  - すべてのゴールは、少なくとも1つのペイン解消またはゲイン創出に紐付く
  - 対応関係が不明確な場合はユーザーに確認する

- **検証セクションの重視**:
  - セクション4（検証）は、ソリューション設計の前に行う
  - 需要の裏付けが弱い場合は、ユーザーにその旨を伝え、追加調査を提案する
  - by nameの顧客がいない場合でも、その事実を正直に記載する

- **コメント部分の扱い**:
  - テンプレート内の `<!-- -->` で囲まれた部分は、執筆のガイダンスです
  - ユーザーとの対話では、このガイダンスを参考にしながら具体的な内容を埋めていきます
  - 最終的なPRDには、ガイダンス部分は残さず、実際の内容のみを記載します

- **具体性の重視**:
  - 抽象的な表現ではなく、具体的な数値や条件を記載します
  - 例: 「高速に動作する」→「200ms以内に応答する」

### セクション間の一貫性チェック（重要）

PRDでは、同じ情報が複数のセクションで参照されます。以下の一貫性を必ず保ってください：

**チェック項目:**
1. **サマリーとゴール**: サマリーで述べた内容がゴールに反映されているか
2. **ペルソナと要件**: ペルソナの属性が要件の対象者と一致しているか
3. **JTBDと要件**: 各JTBDに対応する要件があるか
4. **ペイン/ゲインとゴール**: すべてのゴールがペインまたはゲインに紐付いているか（`(→ P1, G2)` 参照があるか）
5. **KPI整合性とアウトカム指標**: 戦略的KPIとプロジェクト固有のアウトカム指標が整合しているか
6. **MoSCoW優先度**: すべての要件に適切な優先度が設定されているか
7. **行数上限**: 各セクションが上限内に収まっているか。超過時は付録化を提案する

**更新時の注意:**
- あるセクションを変更した場合、関連セクションも確認・更新してください
- 変更漏れは混乱を招くため、変更後に必ず一貫性チェックを実施してください
