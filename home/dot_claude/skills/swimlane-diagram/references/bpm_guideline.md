# 業務プロセス可視化・改善ガイドライン（BPMスタンダード）

## 1. 本ガイドラインの目的
本ドキュメントは、当組織における業務プロセスの可視化および改善活動（BPM）を一元的かつ効率的に進めるための標準手順を定めるものである。

## 2. フェーズ定義
プロセス作成は、以下のステップ順に実施することを原則とする。いきなり図を描き始めるのではなく、必ずStep 1の定義を行ってからStep 2へ進むこと。

| Step | 名称 | 目的 | 主な成果物 |
| :--- | :--- | :--- | :--- |
| **①** | **Identify (特定)** | 改善対象の特定と、評価指標の定義 | ハイレベルプロセスマップ<br>評価指標定義書 |
| **②** | **Discover (現状把握)** | 現状の業務フローの正確な理解 | As-Is プロセスモデル<br>(スイムレーン図) |
| **③** | **Analyze (分析)** | 問題の原因究明と優先順位付け | 分析レポート<br>課題一覧 |
| **④** | **Design (再設計)** | あるべき姿の策定と合意形成 | To-Be プロセスモデル<br>(新スイムレーン図) |

---

## Step 1: Identify - プロセスの特定と指標設定

BPMの実践対象となるプロセスを特定し、「何のために改善するのか」を数値で定義するフェーズである。

### 1-1. プロセスの棚卸と特定
まず、組織全体のプロセスを俯瞰し、改善すべき対象を決定する。

*   **アクション:** 「ハイレベルプロセスマップ（Process Architecture）」を確認・作成する。
*   **対象選定の基準:**
    *   顧客からのクレームが多い領域
    *   処理時間が著しく長い領域
    *   コスト過多となっている領域
    *   *例：A社における「融資申請管理（特に受付・審査）」*

### 1-2. 評価指標（Metrics）の特定
> *"You can't improve what you can’t measure."（測定できないものは改善できない）*

対象プロセスを改善するにあたり、「何をもって良くなったとするか」の指標を事前に定義する。

*   **設定すべき指標 (Process Performance Measures):**
    *   **時間:** リードタイム、処理時間（例：申請から回答までの日数）
    *   **コスト:** 人件費、システム利用料
    *   **品質:** エラー率、手戻り回数、顧客満足度
*   **注意点:** 指標なき改善は、施策の迷走を招くため、必ず着手前に設定すること。

---

## Step 2: Discover - 現状プロセスの理解 (As-Is)

特定されたプロセスの「現在の姿（As-Is）」をありのままに可視化するフェーズである。

### 2-1. As-Is Process Modelの作成
関係者間で認識を共有するため、**スイムレーン（Swimlane）**形式の業務フロー図を作成する。

*   **必須要素:**
    *   誰が（Actor/Swimlane）
    *   何をきっかけに（Event）
    *   何をするか（Activity/Task）
    *   どう判断するか（Gateway）
    *   何を使うか（Object/Artifact）

### 2-2. 情報収集のアプローチ
現状を把握するために、以下の手法を適切に組み合わせる。

| 手法 | 特徴 | 注意点 |
| :--- | :--- | :--- |
| **ヒアリング** | 関係者へのインタビュー。効率的に全体像を把握できる。 | **推奨。** ただし個人の主観が入るため、事実と異なる（盛られている/隠されている）可能性を考慮して裏付けを取ること。 |
| **観察** | 実際の作業現場を見る。正確性が高い。 | 工数が膨大になるため、重要なボトルネック箇所に絞って実施する。 |
| **プロセスマイニング** | システムログから自動可視化。 | システム化されていない手作業（Excelバケツリレー等）は見えないことに注意。 |

---

## Step 3: Analyze - プロセス分析

現状（As-Is）のプロセスを分析し、顕在化している問題や潜在的な問題の原因を探り、対処方法を検討する。

### 3-1. 主な分析手法
問題の性質に合わせて、以下の手法を用いて分析を行う。

| 手法 | 概要 | 目的 |
| :--- | :--- | :--- |
| **サイクルタイム分析** | 業務の実行にかかる時間や日数を測定し、拠点別・担当者別などで比較する。 | 処理遅延の箇所やバラつきを特定する。 |
| **ボトルネック分析** | 伝票処理件数やアウトプット量（スループット）を分析する。 | 全体のパフォーマンスを低下させている「弱点（ボトルネック）」を特定する。 |
| **パターン分析** | 業務の分岐や手戻りの発生パターンを整理する。 | 非効率なフローや例外処理の発生要因を探る。 |
| **相関分析** | 複数の事象間の関係性を分析する。（例：例外処理件数と担当者の職階の相関など） | 問題の根本原因（スキル不足、システム不備など）を特定する。 |
| **パフォーマンス分析** | Step 1で定めた評価指標を用いて、複数の軸（拠点、製品、担当者など）でパフォーマンスの違いを分析する。 | 改善の優先順位を決定するための定量的な根拠を得る。 |

---

## Step 4: Design - プロセス再設計 (To-Be)

分析結果に基づき、あるべき業務の姿（To-Be）を設計し、関係者と合意形成を図る。

### 4-1. 再設計の視点（ECRS）
改善案を検討する際は、以下の「ECRS（イクルス）」のフレームワークを用いて、効果の大きい順に検討する。

| 視点 | 英語 (Meaning) | アクション | 例 |
| :--- | :--- | :--- | :--- |
| **E** | **Eliminate (排除)** | 不要な業務、ルールをなくす | 承認プロセスの廃止、不要な報告書の廃止 |
| **C** | **Combine (結合)** | バラバラの業務をまとめる | 類似業務の統合、担当者の集約、システムの統合 |
| **R** | **Rearrange (入替)** | 業務を整理する、順番を変える | 手順の入れ替え、並行処理化、担当場所の変更 |
| **S** | **Simplify (簡素化)** | 業務を単純化する | 様式の統一、入力項目の削減、テンプレート化 |

### 4-2. To-Be Process Modelの作成
*   検討した施策を実装したプロセスをスイムレーンとして作成する。
*   これを **To-Be Process Model** と呼び、関係者間での共通認識形成に使用する。

### 4-3. 反復的アプローチ
*   AnalyzeとDesignは一度で完了するものではなく、往復しながら進める（Iterative approach）。
*   Designで考えた解決策に実行上の問題が見つかれば、再度Analyzeに戻って別の方向性を検討する柔軟性を持つこと。
