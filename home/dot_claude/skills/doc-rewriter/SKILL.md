# Doc Rewriter

社内向けプロダクト文書をレビュー・リライトするスキル。

## 基本方針

- **読者**: PdM / CS / Eng / Biz などの社内メンバー
- **目的**: 読者が短時間で要点を理解し、意思決定・議論に入れる状態にする
- **トーン**: 「だ・である調」を基本。過度にかしこまらず、フラットで読みやすく

## ワークフロー

### Step 1: 診断（必須）

ドキュメントを読み、以下を診断してユーザーに報告する：

1. **構造の問題**: セクション間の重複、役割のかぶり
2. **分量の問題**: 冗長な説明、同じ主張の繰り返し
3. **表現の問題**: 抽象的修飾語、AI的フレーズ、太字の乱用
4. **論理の問題**: 目的と結論の不整合

診断結果を以下の形式で報告：

```
## 診断結果

### 修正規模: [小 / 中 / 大]

### 検出した問題
1. [問題カテゴリ]: [具体的な問題]
2. ...

### 推奨する修正順序
1. [最初にやること]
2. [次にやること]
3. ...
```

### Step 2: 確認（大規模修正時は必須）

**以下のいずれかに該当する場合、修正前にユーザー確認を取る**：

- セクションの統合・削除・順序変更
- 章構成の大幅な変更
- 内容の50%以上を書き換える必要がある場合

確認時の質問例：
- 「セクションAとBを統合してよいか？」
- 「この章を削除してよいか？」
- 「構成を変更する方針でよいか？」

### Step 3: 修正実行

診断結果の「推奨する修正順序」に従い、順序立てて修正する。

**修正の優先順位**（原則この順で実行）：

1. **重複削除** - 同じ内容の繰り返しを削除
2. **分量圧縮** - 各セクションを要点3〜5文に
3. **修飾語整理** - 抽象的形容詞を削除 or 具体化
4. **太字最適化** - 1セクション3〜5箇所に制限
5. **AI表現除去** - 「〜と言える」等を事実ベースに
6. **構造調整** - セクション統合・順序変更（確認済みの場合のみ）

### Step 4: 差分報告

修正完了後、何を変更したかを簡潔に報告する。

## リライトルール

詳細は [references/rewrite-rules.md](references/rewrite-rules.md) を参照。

### クイックリファレンス

| カテゴリ | ルール |
|---------|--------|
| 分量 | 1パラグラフ最大3文、同じ主張は1回のみ |
| 修飾語 | 「非常に」「大きな」等は数字・具体例と併記 |
| 太字 | 1セクション3〜5箇所、KPI/決定事項/制約のみ |
| AI表現 | 「〜と言える」「〜に寄与する」を禁止 |

## チェックリスト

修正完了時に [references/checklist.md](references/checklist.md) で最終確認を行う。
