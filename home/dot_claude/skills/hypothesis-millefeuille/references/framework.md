# 仮説のミルフィーユ フレームワーク

## 4階層の定義

プロダクトの意思決定を以下の4階層に分類する。上層ほど抽象度が高く、下層への影響力を持つ。

| 階層 | 領域 | 定義・含まれるもの | 変更時の影響範囲 |
|------|------|-------------------|-----------------|
| **Core** | 根幹 | ビジョン、ミッション、事業戦略 | プロダクト全体すべて |
| **Why** | 戦略 | ターゲットユーザー、ペイン/ゲイン、市場定義、競合分析、なぜ自社がやるのか | What, How |
| **What** | 要件 | ユーザー体験(UX)、ビジネスモデル、優先順位(ロードマップ/KPI) | How |
| **How** | 戦術 | UI、設計・実装、GTM(Go To Market)、規約、ドキュメント | ユーザーへの提供形態 |

### 各階層の詳細

#### Core（根幹）
- **含まれるもの**: 会社/事業のビジョン、ミッション、事業戦略
- **問い**: 「私たちは何を目指しているのか？」「どこで勝つのか？」
- **変更頻度**: 数年単位
- **例**:
  - ✅ 良い例: 「地域コミュニティの声を可視化し、社会課題解決を加速する」
  - ❌ 悪い例: 「AIを使ったサービスを作る」（手段が目的化）

#### Why（戦略）
- **含まれるもの**:
  - ターゲットユーザー（ペルソナ、セグメント）
  - ユーザーのペイン（課題）/ ゲイン（得られる価値）
  - 市場定義と競合分析
  - なぜ自社がやるのか（独自性、強み）
- **問い**: 「誰の何を解決するのか？」「なぜ自社がやる意味があるのか？」
- **変更頻度**: 四半期〜年単位
- **例**:
  - ✅ 良い例: 「自治体職員が住民の多様な声を効率的に把握できず、施策が一部の声に偏ってしまう課題を、自社のテキスト分析技術で解決する」
  - ❌ 悪い例: 「若者向けのSNS」（ペインが不明確、競合との差別化なし）

#### What（要件）
- **含まれるもの**:
  - ユーザー体験（UXフロー、ジャーニー）
  - ビジネスモデル
  - 優先順位（ロードマップ、KPI）
- **問い**: 「どのような体験・機能で解決するのか？」「何を先にやるのか？」
- **変更頻度**: 月〜四半期単位
- **例**:
  - ✅ 良い例: 「CSV一括インポート → AI自動分類 → ダッシュボード可視化の3ステップで、職員が1時間以内に全体像を把握できる」
  - ❌ 悪い例: 「便利な機能をたくさん作る」（体験が具体化されていない）

#### How（戦術）
- **含まれるもの**:
  - UI設計
  - 技術実装
  - GTM（Go To Market戦略）
  - 運用規約、ドキュメント
- **問い**: 「どう実現するのか？」「どう届けるのか？」
- **変更頻度**: 週〜月単位
- **例**:
  - ✅ 良い例: 「CSVアップロード画面はドラッグ&ドロップUI、分類はBERTベースのAPIを使用、初期GTMはウェビナー経由」
  - ❌ 悪い例: 「いい感じのUIで作る」（具体性がない）

## Fit & Refineプロセス

階層を一方向に流すのではなく、**往復運動**を繰り返して強度を高める。

### Fit（適合確認）
ある階層を検討した後、**「一つ上の階層と矛盾していないか？」**を確認する作業。

- **目的**: 手段の目的化を防ぐ
- **問い**:
  - What検討後: 「この機能は、本当にターゲットのペイン(Why)を解決しているか？」
  - How検討後: 「このUI/実装は、定義した体験(What)を阻害していないか？」

### Refine（洗練・磨き上げ）
ある階層を検討した知見を使って、**「一つ上の階層をより具体的にできないか？」**をアップデートする作業。

- **目的**: 抽象的な上位概念を、現実的な解像度に引き上げる
- **問い**:
  - What検討後: 「この機能を具体化したことで、ターゲット像(Why)の解像度が上がらないか？ペルソナを書き直すべきではないか？」
  - Why検討後: 「ターゲット分析の結果、事業戦略(Core)の修正が必要ではないか？」

## 階層別チェックリスト

### Core（根幹）
- [ ] 自社のミッション・ビジョンと接続されているか？
- [ ] 事業戦略上の勝ち筋と矛盾していないか？
- [ ] 数年先を見据えた方向性になっているか？

### Why（戦略）
- [ ] **Fit**: Coreの戦略を実現するターゲット選定になっているか？
- [ ] **Refine**: ターゲット分析の結果、Coreの戦略修正が必要ではないか？
- [ ] **肉厚チェック**: ターゲットや課題の仮説は複数検討したか？（思い込みの1つに絞っていないか？）
- [ ] 競合製品と「解決したい課題」レベルで差別化できているか？
- [ ] ターゲットのペインは、本当に存在するか？（仮説検証計画はあるか？）
- [ ] なぜ自社がやるのか、独自性は明確か？

### What（要件）
- [ ] **Fit**: Whyで定義したペインを直接的に解決する体験になっているか？
- [ ] **Refine**: 具体的な体験を考えた結果、ターゲットの定義（Why）にズレは見つからなかったか？
- [ ] **肉厚チェック**: その課題を解決する手段は、今の案以外に10個以上考えたか？その中からなぜこれを選んだのか？
- [ ] 異なるWhyから、たまたま同じWhat（機能）が導き出されていないか？（同床異夢になっていないか確認）
- [ ] 優先順位は明確か？（ロードマップ、KPI設定）
- [ ] ビジネスモデルは持続可能か？

### How（戦術）
- [ ] **Fit**: Whatで定義した体験やビジネスモデルを阻害しないUI/実装か？
- [ ] **Refine**: 実装詳細を詰める中で、要件(What)の無理や不足が見つからなかったか？
- [ ] リリース後の検証計画（何をもって成功とするか）が含まれているか？
- [ ] GTM戦略は明確か？（どうやってユーザーに届けるか？）
- [ ] 運用・サポート体制は考慮されているか？

## トラブルシューティング: 仮説が外れたとき

機能リリース後に成果が出なかった場合、以下の順序で「巻き戻り」を行う。

1. **Howの疑い**: UIや見せ方が悪かっただけではないか？
   - → Howを修正して再検証

2. **Whatの疑い**: UIは良いが、そもそもこの機能（解決策）では課題が解決しないのではないか？
   - → Whatを見直し、別の解決策を検討

3. **Whyの疑い**: 機能は課題を解決しているが、そもそもターゲットにその「痛み」が存在しないのではないか？
   - → Whyに戻り、ユーザーインタビューや市場調査をやり直す

4. **Coreの疑い**: 市場やユーザーニーズは正しいが、事業戦略そのものが間違っているのではないか？
   - → 事業戦略の見直し

## チームへの権限委譲

この4階層が明文化・合意されている場合、以下のような権限委譲が可能になる。

- **Core/Whyが合意済み**: PMやデザイナーはWhat（どのような体験にするか）の決定に集中できる
- **Core/Why/Whatが合意済み**: エンジニアやデザイナーはHow（どう実装・表現するか）を自律的に決定できる

**合言葉**:
- 「迷ったら一つ上の階層に戻ろう」
- 「Fitしてる？ Refineできた？」
