# アプリUI（ダッシュボード・管理画面等）の設計ガイド

SKILL.mdの「成果物タイプ別の検討」をより詳細に解説する。

## アプリUIの目的

Webページ（LP等）との根本的な違いを理解する。

| 観点 | Webページ（LP等） | アプリUI |
|------|------------------|---------|
| 目的 | 説得する、行動を促す | タスクを完了させる |
| 接触頻度 | 1回〜数回 | 継続的に使う |
| 優先事項 | 魅力、説得力 | 効率、使いやすさ |
| 成功指標 | コンバージョン | タスク完了率、時間 |

アプリUIでは「かっこいい」より「迷わない」「速い」が重要。

## 内容設計のフレームワーク

### ユーザーのタスクを起点に考える

```
1. ユーザーは何をしに来るのか（タスク）
2. そのために何が必要か（情報・機能）
3. どういう順序で行うか（フロー）
```

### タスクの洗い出し

```
質問:
- ユーザーが最も頻繁に行う操作は何か
- ユーザーが最も重要だと考える操作は何か
- ユーザーが最初に行う操作は何か
- ユーザーがたまにしか行わない操作は何か

優先度:
頻繁 × 重要 → 最もアクセスしやすく
頻繁 × 重要でない → アクセスしやすく
たまに × 重要 → 見つけやすく
たまに × 重要でない → 隠れていてもOK
```

### 表示すべき情報の整理

```
質問:
- ユーザーが常に見たい情報は何か
- ユーザーが判断・意思決定に必要な情報は何か
- 詳細を見たいときだけ必要な情報は何か
- ほとんど見ない情報は何か

優先度:
常に見たい → 常時表示、目立つ位置
判断に必要 → 関連する操作の近くに
詳細 → 展開・遷移で表示
ほとんど見ない → 設定画面等に隠す
```

## 構成設計のフレームワーク

### 情報階層の設計

```
レベル1: グローバルナビゲーション
- アプリ全体で常に表示
- 主要な機能エリアへの入り口
- 5±2個程度に絞る

レベル2: セクション/ページ
- 特定の機能エリア内の画面
- 関連する情報・操作をまとめる

レベル3: コンポーネント
- カード、テーブル、フォーム等
- 具体的なデータ・操作を含む

レベル4: 詳細・モーダル
- 必要なときだけ表示
- 詳細情報、編集フォーム等
```

### 画面遷移の設計

```
原則:
- 主要タスクは最短経路で到達できる
- 現在地が常に分かる
- 戻る方法が明確
- 関連する画面同士は近くに配置

検証:
- 最も頻繁なタスクは何クリックで完了するか
- ユーザーが「あれどこだっけ」と迷う箇所はないか
- 行き止まりになる画面はないか
```

## ダッシュボード特有の考慮事項

### ダッシュボードの目的を明確に

```
種類:
1. 監視型: 異常があればすぐ分かる
2. 分析型: データを深掘りして洞察を得る
3. 概要型: 全体状況をざっと把握する

それぞれで適切な設計が異なる
```

### 監視型ダッシュボードの場合

```
重要なこと:
- 異常値が一目で分かる（色、アイコン、位置）
- 正常/異常の判断基準が明確
- 異常時のアクションが明確

避けること:
- 情報過多（本当に監視すべきものに絞る）
- 判断基準が曖昧なグラフ
```

### 分析型ダッシュボードの場合

```
重要なこと:
- フィルター、ドリルダウンが柔軟
- データの出典・定義が明確
- エクスポート機能

避けること:
- 固定的すぎる表示（分析の自由度がない）
- 文脈なしの数字の羅列
```

## 仕様書に含めるべき内容

アプリUIの場合、以下を明確にする。

```
### 画面一覧
- [画面名]: [目的・役割]
- [画面名]: [目的・役割]
...

### 主要タスクと導線
- タスク1: [手順、通る画面]
- タスク2: [手順、通る画面]
...

### 各画面の内容
#### [画面名]
- 目的: この画面で何を達成するか
- 表示情報: 何を見せるか
- 操作: 何ができるか
- 遷移: どこに行けるか

### 全体の情報構造
- ナビゲーション構成
- 情報の階層
```
