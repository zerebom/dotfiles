# プランニングスキル

成果物を作る依頼を受けたとき、実装に入る前に「何を作るべきか」を明確にする。

## なぜこのスキルが必要か

曖昧な依頼をそのまま実装すると、以下の問題が起きる。

- 目的に合わない成果物ができる
- 「それっぽいが中身がない」ものになる
- 手戻りが発生する

このスキルで要件を明確化してから実装に進むことで、これらを防ぐ。

## 発動条件

- 「〇〇を作って」「〇〇が欲しい」など成果物の依頼
- 要件が曖昧な状態での制作依頼
- 対象: LP、Webサイト、アプリUI、ダッシュボード、ドキュメント、スライド等

## 基本原則

### 1. 質問は最小限にする

ユーザーを質問攻めにしない。

- 最初に聞くのは1〜3個の本質的な質問のみ
- 残りは「仮で置いて提案 → フィードバックで修正」のサイクルで進める
- ユーザーが既に提供した情報から最大限読み取る

### 2. 仮説を立てて提案する

情報が不足していても、文脈から仮説を立てて先に進む。

```
悪い例: 「ターゲットは誰ですか？目的は何ですか？成功の定義は？競合は？...」

良い例: 「いただいた情報から、以下の前提で進めます。
        - ターゲット: 〇〇（理由: ××から推測）
        - 目的: △△
        違っていれば教えてください」
```

### 3. 具体的に出力する

抽象的な方針ではなく、後段スキルがそのまま使える具体的な仕様を出す。

```
悪い例: 「ユーザーのベネフィットを訴求する見出しにする」

良い例: 「見出し: 『顧客の声を、売上につながる施策へ。』
        理由: ターゲット（マーケ担当者）の課題（VoC活用できていない）に
        直接応える形にした」
```

## プロセス

### Step 1: 要件の把握

依頼内容から以下を特定する。

| 項目 | 確認すること |
|------|-------------|
| 成果物の種類 | 何を作るのか（LP、アプリUI、ドキュメント等） |
| 提供された情報 | ユーザーが既に伝えてくれていること |
| 不足している情報 | 進めるために最低限必要だが、不明なこと |

不足情報が多い場合は、最も重要な1〜3点のみ質問する。

### Step 2: 5つの問いに答える

どんな成果物でも、以下の5つを明確にする。

#### 問い1: 目的（何のために作るのか）

- この成果物で達成したいことは何か
- 成功とは何か（どうなれば目的達成か）
- 副次的な目的はあるか

#### 問い2: 対象（誰のために作るのか）

- 誰がこれを見る/使うのか
- その人の立場、役割、文脈は何か
- その人の前提知識はどの程度か
- その人は何を求めている/困っているか

#### 問い3: 内容（何を伝える/実現するのか）

- 必ず含めるべきことは何か
- 優先順位はどうか（必須/重要/あれば良い）
- 含めるべきでないことは何か
- 曖昧にしてはいけないことは何か

#### 問い4: 構成（どういう順序・構造で）

- どういう流れで組み立てるか
- 各パートの役割は何か
- 全体として論理的に繋がっているか
- 対象者の思考の流れに沿っているか

#### 問い5: 表現方針（どういう印象・トーンで）

- どういう印象を与えたいか
- 適切なトーンは何か
- 避けるべき表現は何か

## 成果物タイプ別ガイド

5つの問いに答える際、成果物タイプに応じて考慮すべき観点が異なる。

### Webページ（LP、コーポレートサイト等）の場合

**内容の設計で考慮すること:**
- 伝えるべきメッセージの核は何か
- ユーザーにどんな行動を取ってほしいか（CTA）
- CTAは目的・対象と整合しているか
- 見出し・本文で使う言葉は対象者に伝わるか

**プロダクトのビジュアル表現（SaaS LPの場合は必須）:**
- 実際のUI画面、ダッシュボードのスクリーンショット
- 画面がない場合は、モックアップを設計する
- 抽象的な図形やイメージ画像だけでは不十分

**信頼の証（Social Proof）:**
- 導入企業ロゴ（Trust Bar）
- 導入社数、実績数値
- 受賞歴、認証、メディア掲載
- レビューサイトの評価

**構成の設計で考慮すること:**
- ファーストビューで何を見せるか
- スクロールに沿ってどう説得していくか
- 情報の順序は対象者の関心の流れに沿っているか

**表現方針で考慮すること:**
- 信頼性が必要か、親しみやすさが必要か
- 競合と比べてどう差別化するか

**よくある失敗:**
- 専門用語を説明なく使う
- 機能の説明に終始し、ベネフィットがない
- CTAが複数あり、動線が散漫
- プロダクトUIを見せず、文字だけで説明する
- 信頼の証がなく、「誰も使っていない」印象を与える

### アプリUI（ダッシュボード、管理画面等）の場合

**内容の設計で考慮すること:**
- ユーザーが達成したいタスクは何か
- 表示すべきデータ・情報は何か
- 優先度の高い情報は何か
- ユーザーの操作フローはどうあるべきか

**構成の設計で考慮すること:**
- 情報の階層構造はどうなっているか
- 画面遷移はどうあるべきか
- 頻繁に使う機能へのアクセスは容易か

**表現方針で考慮すること:**
- 効率性重視か、学習しやすさ重視か
- データの視認性は十分か

**よくある失敗:**
- 情報を詰め込みすぎる
- ユーザーのタスクフローを考慮しない
- 見た目重視で操作性を犠牲にする

### ドキュメント（提案書、レポート等）の場合

**内容の設計で考慮すること:**
- 主張・結論は何か
- その根拠は何か
- 読み手に求めるアクションは何か
- 想定される反論・疑問は何か

**構成の設計で考慮すること:**
- 結論から入るか、背景から入るか
- 論理の流れは明確か
- 章立て・見出しで全体像が把握できるか

**表現方針で考慮すること:**
- フォーマル度合いはどの程度か
- 図表をどの程度使うか

**よくある失敗:**
- 結論が最後までわからない
- 根拠が弱い、または飛躍がある
- 読み手の前提知識を考慮しない

### プレゼンテーション（スライド等）の場合

**内容の設計で考慮すること:**
- 1スライド1メッセージになっているか
- 聴衆が持ち帰るべきことは何か
- 口頭説明とスライドの役割分担は明確か

**構成の設計で考慮すること:**
- 導入→本論→結論の流れは明確か
- 聴衆の関心を引く導入になっているか
- 時間配分は適切か

**表現方針で考慮すること:**
- 文字量は適切か（多すぎないか）
- 視覚的な強弱は明確か

**よくある失敗:**
- 文字が多すぎて読めない
- スライドと口頭説明が重複
- 構成が散漫で記憶に残らない

## 出力フォーマット

5つの問いへの回答を、以下の形式で仕様書として出力する。

```markdown
# 仕様書: [成果物名]

## 前提

### 目的
[この成果物で達成したいこと]

### 対象
[誰のためのものか、その人の文脈]

### 成功の定義
[どうなれば成功か]

## 内容

### 必須要素
[必ず含めるべきこと]

### 優先度の高い要素
[できれば含めたいこと]

### 含めないこと
[意図的に除外すること、その理由]

## 構成

[全体の流れ、各パートの役割]

## 表現方針

### トーン
[どういう印象を与えたいか]

### 避けるべきこと
[やってはいけないこと]

## 具体的な内容（成果物タイプに応じて）

[見出し案、画面構成案、章立て案など]
```

---

## 確認のステップ

仕様書を出力したら、ユーザーに確認を取る。

```
この内容で実装に進んでよいでしょうか？
修正したい点があれば教えてください。
```

確認が取れたら、後段の実装スキルに引き継ぐ。
