# レビューチェックリスト（6軸）

各観点のチェック項目と、典型的な指摘例。

---

## 1. ビジネス

課題が本物か、解く価値があるか、測れるかを検証する。

### チェック項目

- [ ] **課題の実在性**: ペインは推測ではなく、顧客インタビューやデータで裏付けられているか？
- [ ] **ターゲットの解像度**: ペルソナが「全ユーザー」のように曖昧でないか？具体的な属性・規模があるか？
- [ ] **市場の大きさ**: TAM/SAMの見積もりがあるか？少なくとも対象顧客数の桁感はあるか？
- [ ] **競合との差別化**: 競合の同等機能と比較して、なぜ自社がやるべきかが明確か？
- [ ] **KPI設計**: 成功指標が計測可能か？現状値と目標値があるか？
- [ ] **ROI/投資対効果**: 開発コストに見合うリターンの見込みがあるか？
- [ ] **需要の具体性**: by nameで顧客名が挙がっているか？（少なくとも3社以上が望ましい）
- [ ] **優先度の根拠**: なぜ今やるのか？他の施策と比較した根拠があるか？

### 指摘例

- P0: 「課題の裏付けが推測のみ。顧客インタビュー結果やCSからのフィードバックを追加してください」
- P1: 「KPIに『利用率向上』とあるが、現状値・目標値・測定方法が未定義。計測可能な形に書き直してください」
- P2: 「競合比較がないため、差別化ポイントが不明確。簡易な競合分析の追加を推奨」

---

## 2. デザイン/UX

ユーザーが迷わず使えるか、エッジケースで破綻しないかを検証する。

### チェック項目

- [ ] **ユーザーフロー**: 主要なハッピーパスが明示されているか？
- [ ] **エントリーポイント**: ユーザーがこの機能にどこからたどり着くかが定義されているか？
- [ ] **エラー/例外フロー**: ネットワークエラー、空データ、権限不足時のUXが定義されているか？
- [ ] **エッジケース**: 大量データ、長文入力、同時操作、初回利用/0件状態は考慮されているか？
- [ ] **情報設計**: 画面に載せる情報量は適切か？優先順位は明確か？
- [ ] **既存フローへの影響**: 既存ユーザーの慣れたワークフローを壊さないか？
- [ ] **オンボーディング**: 初回利用時の導線は考慮されているか？
- [ ] **アクセシビリティ**: 必要に応じてスクリーンリーダー、キーボード操作、色覚対応は検討されているか？

### 指摘例

- P0: 「ユーザーフローの記述がなく、UIの振る舞いが読み取れない。主要フローを追加してください」
- P1: 「データが0件の場合のEmpty Stateが未定義。初回利用のUXを検討してください」
- P2: 「一覧画面の項目が10個以上あり、情報過多の可能性。優先表示項目の整理を推奨」

---

## 3. 技術

実現可能か、既存システムと整合するか、将来に負債を残さないかを検証する。

### チェック項目

- [ ] **実現可能性**: 要件に対して技術的に不可能または極めて困難な箇所はないか？
- [ ] **アーキテクチャ影響**: 既存のDB構造、API設計、マイクロサービス構成と矛盾しないか？
- [ ] **データモデル**: 新規テーブルやスキーマ変更が必要な場合、マイグレーション方針はあるか？
- [ ] **パフォーマンス**: 想定データ量・リクエスト量に対するレスポンスタイムの要件はあるか？
- [ ] **スケーラビリティ**: ユーザー/データが10倍になった場合に破綻しない設計か？
- [ ] **セキュリティ**: 認証/認可、入力バリデーション、データ暗号化は考慮されているか？
- [ ] **外部依存**: サードパーティAPI、ライブラリの依存とそのリスクは把握されているか？
- [ ] **技術的負債**: 今回の実装が将来の拡張を阻害しないか？

### 指摘例

- P0: 「リアルタイム音声処理を要求しているが、現在のインフラ構成では遅延要件を満たせない可能性が高い。技術検証（PoC）を先に実施してください」
- P1: 「既存のユーザーテーブルにカラム追加が必要だが、マイグレーション計画が未記載。ダウンタイムの有無を明記してください」
- P3: 「WebSocket採用を検討してもよいかもしれない（現状のポーリングでも要件は満たせる）」

---

## 4. 法務/コンプライアンス

法的リスク、個人情報の取り扱い、規約への影響を検証する。

### チェック項目

- [ ] **個人情報の取得/保存**: 新たに取得する個人情報はあるか？利用目的は明示されているか？
- [ ] **同意取得**: 個人情報の取得にユーザーの明示的同意が必要か？同意フローは設計されているか？
- [ ] **データ保持/削除**: データの保持期間、削除ポリシーは定義されているか？
- [ ] **利用規約/プライバシーポリシー**: 規約の改訂が必要な変更はないか？
- [ ] **第三者提供**: データを外部サービスに送信する場合、適切な契約・同意があるか？
- [ ] **業界規制**: 対象業界固有の規制（金融、医療、教育等）への対応は必要か？
- [ ] **AI/機械学習**: AIによる判断がある場合、説明責任や公平性は検討されているか？
- [ ] **著作権/知的財産**: 他者のコンテンツを利用する機能の場合、権利処理は考慮されているか？

### 指摘例

- P0: 「通話音声をAI分析に利用するが、録音の同意取得フローが未定義。個人情報保護法上、明示的同意が必須」
- P1: 「外部AI APIにデータを送信する設計だが、データ処理委託契約（DPA）の締結要否が未検討」
- P2: 「データ保持期間の記載がない。デフォルトの保持ポリシーを明記してください」

### 適用判断

このPRDに法務観点が不要と判断した場合（例: UIの見た目変更のみ）、「法務/コンプライアンス: 該当なし（理由: ...）」として省略してよい。

---

## 5. 運用

リリース後にCSや運用チームが困らないかを検証する。

### チェック項目

- [ ] **CS影響**: 問い合わせ増加の見込みはあるか？FAQやヘルプ記事の準備は計画されているか？
- [ ] **説明コスト**: CSが顧客に説明する際、一言で説明できるか？（説明が複雑 = UX問題の可能性）
- [ ] **移行計画**: 既存データや設定のマイグレーション手順はあるか？
- [ ] **段階ロールアウト**: 一斉リリースか、段階的リリースか？ベータ/カナリアの計画はあるか？
- [ ] **モニタリング**: リリース後に監視すべきメトリクスとアラート条件は定義されているか？
- [ ] **ロールバック**: 問題発生時のロールバック手順と判断基準はあるか？
- [ ] **ドキュメント**: 社内wiki、リリースノート、変更ログの更新計画はあるか？
- [ ] **サポート体制**: リリース直後の問い合わせ増に対する体制は検討されているか？

### 指摘例

- P1: 「既存テナントのデータ移行手順が未定義。移行失敗時のロールバック方法も含めて追加してください」
- P2: 「モニタリング指標の記載がない。リリース後にOKR/KPIの推移を追跡する仕組みを検討してください」
- P3: 「ベータリリースの対象顧客候補があると、段階ロールアウトの計画が立てやすくなります」

---

## 6. 戦略整合（ミルフィーユ）

PRDが上位戦略と一貫しているかを、仮説のミルフィーユ（Core/Why/What/How）の枠組みで検証する。

### チェック項目

- [ ] **Core → Why**: このPRDが解く課題は、事業戦略・ビジョンと整合しているか？
- [ ] **Why → What**: 定義した課題/ターゲットに対して、ソリューションが直接的に応えているか？（手段の目的化はないか？）
- [ ] **What → How**: 要件に対して、設計/実装方針が適切に対応しているか？
- [ ] **ロードマップ整合**: 今期/今Qのロードマップ上の位置づけは明確か？
- [ ] **リソース整合**: チームのキャパシティとスコープは整合しているか？
- [ ] **他施策との関係**: 並行する他の施策と矛盾や重複はないか？
- [ ] **階層の薄さ**: 各階層で複数の選択肢を検討した形跡があるか？（最初のアイデアをそのまま採用していないか？）

### 指摘例

- P0: 「事業戦略では『エンタープライズ顧客の深耕』を掲げているが、このPRDのターゲットはSMB。戦略との整合を説明してください」
- P1: 「Why（課題）とWhat（機能）の間に飛躍がある。『なぜこの機能が課題を解くのか』のロジックを補強してください」
- P2: 「ソリューションの代替案の検討が見当たらない。他のアプローチを検討した上での選定理由を追記すると説得力が増します」

レビュー精度を高めるために、以下を参照する（存在する場合）:

- `work/products/voice/strategy/` 配下の戦略ドキュメント
- ミルフィーユのワーキングドキュメント
- 今期のOKR/ロードマップ

## 7. Voice PRD スタイル整合（Voiceチーム PRD 固有）

レビュー対象が Voice チームの PRD（`creating-prd` テンプレート準拠）の場合に追加で確認する構造チェック。SSoT は [work/products/voice/prds/2026-03-30-x-api-integration/prd.md](../../../ghq/github.com/zerebom/pm-docs/work/products/voice/prds/2026-03-30-x-api-integration/prd.md) のスタイル。Voice 以外の PRD では該当なしとしてスキップしてよい。

### チェック項目

- [ ] **ペインラベル**: 3.3 のペインが `**P1**:` `**P2**:` `**P3**:` のラベル付き箇条書きで書かれているか。表形式や、独立した「ゲイン」セクションが残っていないか（ゲインは5.1 ゴールに折り畳む方針）
- [ ] **ゴール番号 + ペイン参照**: 5.1 の各ゴールが `**G1. タイトル**（→ P1, P3）` の形で、対応するペイン番号を明示しているか
- [ ] **要件のゴール別ネスト**: 5.2 の要件が **G1 / G2 / G3 ごとにサブセクションが切られ、各ゴール内で Must / Should / Could が配置**されているか。全要件がフラットに MoSCoW だけで並んでいないか
- [ ] **要件1行ルール**: 5.2 の各要件が **1行の箇条書き**で、動作・成果物が一読で分かる粒度か。ユーザーストーリー形式（"〜として〜したい"）や、1要件3行以上の長文になっていないか
- [ ] **Won't の集約**: Won't が各ゴール内に散っておらず、**5.2 末尾にカテゴリ別**（例: 〇〇関連 / UX関連 / ゴール横断）で集約されているか。各項目に「今回やらない理由」が添えられているか
- [ ] **エラー/例外の表**: 5.2 末尾に `#### エラー/例外時の挙動` の表があり、シナリオ / ユーザーが見る画面 / システム挙動 の3列で異常系が整理されているか
- [ ] **縦参照の整合**: 3.3 の P1/P2/P3 と 5.1 の `（→ Pn）` 参照、5.1 の G1/G2/G3 と 5.2 のサブセクションが1対1で対応し、ズレや孤立がないか
- [ ] **背景のインライン構造**: 2. 背景と経緯が `**起点**:` `**経緯**:` `**なぜ今か**:` のインラインボールドで書かれ、h3で階層を切っていないか

### 指摘例

- P1: 「3.3 ペインが表形式で書かれており、後段のゴール（5.1）から番号参照できません。`**P1**:` `**P2**:` ... のラベル付き箇条書きに揃えてください」
- P1: 「5.2 要件が Must/Should/Could でフラットに並んでおり、どのゴールに紐づく要件か読み取れません。G1/G2/G3 ごとにサブセクションを切り、各ゴール内で MoSCoW を配置してください」
- P2: 「5.1 のゴールに `（→ Pn）` のペイン参照がなく、P2 に紐づくゴールが特定できません。ゴール追加かノンゴール明示をお願いします」
- P2: 「Won't が Must/Should と同じ階層で G1 の中に入っています。全ゴール横断のスコープ外項目は 5.2 末尾にカテゴリ別で集約してください」
- P2: 「要件に『ユーザーは〜として、〜したい、なぜなら〜』のユーザーストーリー形式が混ざっています。1行の動作記述に書き換えてください」
