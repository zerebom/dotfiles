# PRD Review - 多角的レビュー

PRDの中身を6つの専門観点からレビューし、優先度付きのフィードバックを返す。

## 既存スキルとの違い

| | prd-review | doc-rewriter | doc-distiller | creating-prd |
|---|---|---|---|---|
| 対象 | PRDの中身の妥当性 | 文章の表層品質 | 構造・概念レベル | PRD新規作成 |
| 観点 | 6軸の専門レビュー | AI表現・太字・冗長 | 膨張・残渣・散在 | 対話的共創 |
| 出力 | 優先度付き指摘リスト | 修正済みファイル | 蒸留済みファイル | PRDファイル |

連携例: creating-prd → **prd-review** → doc-rewriter（内容確定後に文章品質を仕上げ）

## ワークフロー

### Step 1: PRD読み込みとコンテキスト把握

PRDを通読し、以下を把握する:

- 文書の対象プロダクト/機能
- 想定読者（承認者は誰か）
- フェーズ（ドラフト / レビュー待ち / 承認済み）
- 関連する戦略ドキュメントの有無

戦略ドキュメントがある場合（`work/products/` 配下や、ユーザー指定のパス）、戦略整合レビューの精度が上がるため読み込む。

### Step 2: 6軸レビュー実行

[references/checklists.md](references/checklists.md) に基づき、6つの観点からレビューする。

各観点で指摘を洗い出し、以下の優先度を付与:

| 優先度 | 意味 | アクション |
|--------|------|-----------|
| **P0: Blocker** | これが未解決だとPRD承認不可 | 承認前に必ず対応 |
| **P1: Major** | 品質に重大な影響。放置するとリスク | 強く対応を推奨 |
| **P2: Minor** | 改善すればよりよくなる | 余裕があれば対応 |
| **P3: Suggestion** | 参考意見 | 任意 |

### Step 3: レビュー結果の報告

以下の形式で報告する:

```
## PRDレビュー結果

**対象**: {PRD名}
**レビュー日**: {日付}
**総合評価**: {A: 承認可 / B: 軽微な修正後承認可 / C: 要修正 / D: 大幅見直し}

### サマリー

{2-3文で全体の所感。最も重要な問題を端的に}

### 指摘一覧

#### P0: Blocker ({件数})

| # | 観点 | 指摘 | 該当箇所 | 推奨アクション |
|---|------|------|----------|---------------|
| 1 | {観点名} | {指摘内容} | {セクション/行} | {具体的な改善案} |

#### P1: Major ({件数})
...

#### P2: Minor ({件数})
...

#### P3: Suggestion ({件数})
...

### 観点別サマリー

| 観点 | 評価 | 主な指摘 |
|------|------|---------|
| ビジネス | {○/△/×} | {一言} |
| デザイン/UX | {○/△/×} | {一言} |
| 技術 | {○/△/×} | {一言} |
| 法務/コンプライアンス | {○/△/×} | {一言} |
| 運用 | {○/△/×} | {一言} |
| 戦略整合 | {○/△/×} | {一言} |
```

### Step 4: ユーザーとの対話

報告後、ユーザーの反応に応じて:

- **「直して」**: P0/P1の指摘を反映してPRDを修正する
- **「詳しく」**: 特定の指摘について深掘りする
- **「この観点だけ」**: 指定された観点のみ詳細レビューする
- **「doc-rewriter もかけて」**: 内容修正後に文章品質を仕上げる

## 6つのレビュー観点

詳細なチェック項目は [references/checklists.md](references/checklists.md) を参照。

### 1. ビジネス
課題定義の妥当性、ターゲット/市場の解像度、KPI設計、ROI/優先度の根拠

### 2. デザイン/UX
ユーザーフロー、情報設計、エッジケース/エラー体験、アクセシビリティ

### 3. 技術
実現可能性、アーキテクチャ影響、パフォーマンス/スケーラビリティ、技術的負債

### 4. 法務/コンプライアンス
個人情報/プライバシー、利用規約/約款影響、業界規制、データ保持/削除

### 5. 運用
CS影響（問い合わせ/説明コスト）、移行計画、モニタリング/アラート、ロールバック

### 6. 戦略整合（ミルフィーユ）
Core/Why/What/How の一貫性、上位戦略との整合、ロードマップ上の位置づけ

### 7. Voice PRD スタイル整合（Voiceチーム PRD のみ）
`creating-prd` テンプレート準拠の構造チェック。ペインの P1/P2/P3 ラベル、ゴールの G1/G2/G3 + `（→ Pn）` 参照、5.2 要件の「ゴール単位ネスト × MoSCoW × 1行箇条書き」構造、Won't のカテゴリ別集約、エラー/例外表の有無など。Voice 以外の PRD では該当なしとしてスキップする。

## レビューの心構え

- **指摘は具体的に**: 「曖昧です」ではなく「セクションXの〇〇が△△なので、□□を追加すべき」
- **推奨アクションを必ず添える**: 問題提起だけで終わらない
- **PRDのフェーズを考慮**: ドラフト段階ならP2/P3は控えめに。承認直前なら網羅的に
- **ないものは指摘しない**: 法務観点が不要な機能に法務レビューを強要しない
