# Linear Voice Issue 作成スキル

## タイトルと本文の表記ルール

Linear の Issue はそれ単体で読んで意味が通る状態（self-contained）を保つ。次の表記は禁止する。

- **造語ID / 仮IDの使用禁止**: `NEW-1` `TICKET-A` `NEW-仮` など、Linear に存在しない識別子で他チケットを参照しない。Linear 上でリンクが張られず、読み手がどのチケットか特定できない。未起票のチケットを参照するときは、タイトル相当の短い説明文（例:「初回取得フロー（過去90日自動取得）」）で書く。起票後に Linear ID を補記するフローにする。
- **ドキュメントの節番号の使用禁止**: `§5.4.3` `PRD 5.3.2` のような節番号だけで PRD / 仕様書を参照しない。節番号はドキュメント改版で変わる上、Linear 上でリンクにならない。節名（例:「PRD: データモデル節」「PRD: ゴール2 Must」）で書くか、該当ドキュメントの URL を併記する。
- **略号・内部ジャーゴン**: L0/L2 フィルタ、バックフィル、404再取得、Display Requirements のような略号・造語はタイトルから外す。本文中でも初出で 1 行の補足説明をつける。
- **抽象名詞単独のタイトル**: 「UI」「パイプライン」「モジュール」だけのタイトルにしない。何を見せる / 何を流す処理かを動詞ベースで書く（例:「クロス集計結果をヒートマップで表示する」）。

### 他 Issue への参照の書き方

Linear Web エディタでは `VOI-664` と入力するとインラインカード化されるが、**CLI / API 経由で Markdown を投入した場合、プレーンテキストの `VOI-664` が必ずリンク化されるとは限らない**。確実にクリックで飛べる状態にするため、既起票 Issue を参照するときは以下のいずれかを使う。

- Issue の URL をそのまま貼る（自動で Issue カードにアンファールされる）: `https://linear.app/<workspace>/issue/VOI-664`
- もしくは Markdown リンクで書く: `[VOI-664 データモデル拡張](https://linear.app/<workspace>/issue/VOI-664)`

短く参照したい場合は文中に `VOI-664` と ID だけ書いてもよい（読み手は ID 検索で辿れる）が、その場合も 初出時に一度は URL か Markdown リンクを置く。

OK な参照:
- 既起票の Linear Issue → Issue URL を貼る、もしくは `[VOI-664](URL)` で書く
- 未起票の関連チケット → 「月間取得上限・自動停止（新規チケット）」のように説明文で
- ドキュメント参照 → 「PRD: データモデル節」と節名で、URL があれば併記

## Issue 構造

Issue の `description` は以下の5セクションで構成する。各セクションは Markdown の H3 見出し（`###`）で記載。

### 1. 概要 (Summary)

- Issue の要点を 3〜5 行で記述
- 誰が、どの文脈で、何に困っている / 何をしたいか
- この Issue で解決・達成したいこと
- Voice / AI チャット固有であれば明記

### 2. 受け入れ要件 (Acceptance Criteria)

- 「完了」の定義を箇条書きで 3〜7 個
- 可能であれば Given / When / Then 形式
- Voice / AI チャット向け観点:
  - レスポンスのレイテンシ（体感速度）
  - 回答品質（誤回答がないか、意図したコンテキストが使われているか）
  - フォールバック動作（LLM エラー時・タイムアウト時の UX）
  - ログ / メトリクス（どのイベントを計測するか）

### 3. 実装の補足情報 (Implementation Notes)

- アーキテクチャ / 変更箇所（フロント / BFF / API / ジョブなど）
- 既存の関連コード・モジュール
- 技術的な制約・トレードオフ・検討済みの案
- LLM や外部 API のコスト/レートリミットに関する前提
- 詳細仕様は別ドキュメントに切り出し可（リンクと要約を記載）

### 4. テスト観点 (Test / QA Notes)

- メインフロー（ハッピーパス）での確認手順
- エッジケース / 例外系（API エラー、タイムアウト、ネットワーク不良など）
- Voice / AI チャット特有の観点:
  - モバイル / デスクトップの両方で問題ないか
  - 多言語入力 / 絵文字 / 記号などに問題がないか
  - レイテンシ・スロットリングが UX に悪影響を与えていないか

### 5. 関連情報 (Reference)

- PRD / 仕様書へのリンク（`product-spec/` 配下など）
- Figma / デザインプロトタイプへのリンク
- ユーザーストーリーマッピングやメモへのリンク
- 参考になった過去 Issue / チケット

## 作成手順

1. ユーザーから概要・要件の素案を収集
2. 上記5セクションを埋める形で description を Markdown ファイルとして組み立てる
3. Linear CLI で Issue を作成:
   ```bash
   linear issue create --team Voice -t "タイトル" --description-file /tmp/issue-desc.md --no-interactive
   ```
   - description は一時ファイルに書き出して `--description-file` で渡す（Markdown の改行・特殊文字を安全に扱える）
   - 必要に応じて `--assignee`, `--priority`, `--label`, `--project` オプションを付与
