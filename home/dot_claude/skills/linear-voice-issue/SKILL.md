# Linear Voice Issue 作成スキル

Linear の MCP サーバー（`mcp__linear-server__save_issue` ほか）経由で、Voice / AI チャット関連の Issue を一貫した構造で起票する。CLI（`linear` コマンド）は使わない。

## デフォルト設定

- **チーム**: Voice
- **担当者**: me
- **ステータス**: Backlog

チーム / ラベル / プロジェクト / ステータスの ID が不明なときは、先に `mcp__linear-server__list_teams` / `mcp__linear-server__list_issue_labels` / `mcp__linear-server__list_projects` / `mcp__linear-server__list_issue_statuses` で取得する。

## モード判定

ユーザーの依頼内容に応じて、以下のいずれかのモードで進める。

### クイックモード

- **発動条件**: 要件が明確に提示されている場合
  - 「〇〇の Issue を作って」「〇〇のチケットを起票して」
  - タイトル・要件・背景が具体的に述べられている
- **フロー**: 要件整理 → description 組み立て → 起票

### ディスカッションモード

- **発動条件**: 要件が曖昧、または相談・議論を求めている場合
  - 「〇〇のチケットを作りたいのでディスカッションしたい」
  - 「〇〇について相談したい」「〇〇どうしようか」
  - 課題は見えているが、解決策やスコープが未確定
- **フロー**: 下記の「ディスカッションフェーズ」を実施してから起票

## ディスカッションフェーズ

要件が曖昧な場合、以下のステップでユーザーと対話しながら要件を固める。

### Step 1: 現状調査

- **技術系 Issue**（ライブラリ更新、リファクタリング等）の場合:
  - コードベースを調査し、関連する実装の現状を把握する
  - アーキテクチャ、処理フロー、ボトルネックを整理する
  - Explore エージェントを活用して効率的に調査する
- **機能系 Issue**（新機能、機能改善等）の場合:
  - 仕様や要件の整理に集中する（コードの調査は不要）

### Step 2: 論点の提示

- 調査結果をユーザーに共有する（現状のアーキテクチャ図、処理フローなど）
- チケットの切り方・スコープについて選択肢を提示する
- 技術的な判断が必要な箇所を明示して質問する
  - 例: 「並列化の対象は後段の4フローという理解で合ってますか？」
  - 例: 「通知手段は Slack / メール / アプリ内のどれを想定していますか？」

### Step 3: 要件の確定

- ユーザーの回答を受けて、要件を確定する
- 複数チケットに分割すべきかを判断し、提案する
- 確定した要件で Issue 構造を組み立てる

### Step 4: 起票

- 下記の「作成手順」に従って起票する
- 複数チケットの場合は依存関係も設定する

## タイトルと本文の表記ルール

Linear の Issue はそれ単体で読んで意味が通る状態（self-contained）を保つ。次の表記は禁止する。

- **造語ID / 仮IDの使用禁止**: `NEW-1` `TICKET-A` `NEW-仮` など、Linear に存在しない識別子で他チケットを参照しない。Linear 上でリンクが張られず、読み手がどのチケットか特定できない。未起票のチケットを参照するときは、タイトル相当の短い説明文（例:「初回取得フロー（過去90日自動取得）」）で書く。起票後に Linear ID を補記するフローにする。
- **ドキュメントの節番号の使用禁止**: `§5.4.3` `PRD 5.3.2` のような節番号だけで PRD / 仕様書を参照しない。節番号はドキュメント改版で変わる上、Linear 上でリンクにならない。節名（例:「PRD: データモデル節」「PRD: ゴール2 Must」）で書くか、該当ドキュメントの URL を併記する。
- **略号・内部ジャーゴン**: L0/L2 フィルタ、バックフィル、404再取得、Display Requirements のような略号・造語はタイトルから外す。本文中でも初出で 1 行の補足説明をつける。
- **抽象名詞単独のタイトル**: 「UI」「パイプライン」「モジュール」だけのタイトルにしない。何を見せる / 何を流す処理かを動詞ベースで書く（例:「クロス集計結果をヒートマップで表示する」）。

### 他 Issue への参照の書き方

Linear Web エディタでは `VOI-664` と入力するとインラインカード化されるが、**MCP / API 経由で Markdown を投入した場合、プレーンテキストの `VOI-664` が必ずリンク化されるとは限らない**。確実にクリックで飛べる状態にするため、既起票 Issue を参照するときは以下のいずれかを使う。

- Issue の URL をそのまま貼る（自動で Issue カードにアンファールされる）: `https://linear.app/<workspace>/issue/VOI-664`
- もしくは Markdown リンクで書く: `[VOI-664 データモデル拡張](https://linear.app/<workspace>/issue/VOI-664)`

短く参照したい場合は文中に `VOI-664` と ID だけ書いてもよい（読み手は ID 検索で辿れる）が、その場合も初出時に一度は URL か Markdown リンクを置く。

OK な参照:
- 既起票の Linear Issue → Issue URL を貼る、もしくは `[VOI-664](URL)` で書く
- 未起票の関連チケット → 「月間取得上限・自動停止（新規チケット）」のように説明文で
- ドキュメント参照 → 「PRD: データモデル節」と節名で、URL があれば併記

## Issue 構造

Issue の `description` は以下の5セクションで構成する。各セクションは Markdown の見出しで記載。

### 1. 概要 (Summary)

- Issue の要点を 3〜5 行で記述
- 誰が、どの文脈で、何に困っている / 何をしたいか
- この Issue で解決・達成したいこと
- Voice / AI チャット固有であれば明記

### 2. 受け入れ要件 (Acceptance Criteria)

- 「完了」の定義をチェックボックス付き箇条書きで 3〜7 個
- 計測可能・検証可能な基準にする。可能であれば Given / When / Then 形式
- Voice / AI チャット向け観点（該当する場合）:
  - レスポンスのレイテンシ（体感速度）
  - 回答品質（誤回答がないか、意図したコンテキストが使われているか）
  - フォールバック動作（LLM エラー時・タイムアウト時の UX）
  - ログ / メトリクス（どのイベントを計測するか）

### 3. 実装の補足情報 (Implementation Notes)

- **技術系 Issue**（ライブラリ更新、リファクタリング等）の場合:
  - アーキテクチャ / 変更箇所（フロント / BFF / API / ジョブなど）
  - 既存の関連コード・モジュール（ディスカッションで調査した内容を反映）
  - 技術的な制約・トレードオフ・検討済みの案
  - LLM や外部 API のコスト/レートリミットに関する前提
- **機能系 Issue**（新機能、機能改善等）の場合:
  - 仕様・振る舞いの説明にとどめる（具体的な修正箇所やコードパスは記載しない）
  - UI/UX の期待動作、データの流れなど仕様レベルの補足のみ
- 詳細仕様は別ドキュメントに切り出し可（リンクと要約を記載）

### 4. テスト観点 (Test / QA Notes)

- メインフロー（ハッピーパス）での確認手順
- エッジケース / 例外系（API エラー、タイムアウト、ネットワーク不良など）
- Voice / AI チャット特有の観点:
  - モバイル / デスクトップの両方で問題ないか
  - 多言語入力 / 絵文字 / 記号などに問題がないか
  - レイテンシ・スロットリングが UX に悪影響を与えていないか

### 5. 関連情報 (Reference)

- PRD / 仕様書へのリンク（`product-spec/` 配下など）
- Figma / デザインプロトタイプへのリンク
- ユーザーストーリーマッピングやメモへのリンク
- 参考になった過去 Issue / チケット

## 作成手順

### 1. Issue 内容の整理

ユーザーから提供された情報をもとに、上記5セクションに沿って description を Markdown として組み立てる。

タイトルや概要が不明な場合は AskUserQuestion で確認してから進む。情報が不足しているセクションは AskUserQuestion で確認するが、すべてのセクションを埋める必要はなく、わかる範囲で記載すればよい。

### 2. Priority の確認

AskUserQuestion を使って Priority を確認する。選択肢：

- No Priority (0)
- Urgent (1)
- High (2)
- Medium (3)
- Low (4)

ユーザーが引数や会話の中で Priority を明示した場合は確認をスキップしてよい。

### 3. Issue 作成

`mcp__linear-server__save_issue` を使って以下の設定で作成する：

- **title**: 簡潔で具体的なタイトル（機能領域: 内容）
- **team**: Voice
- **assignee**: me
- **state**: Backlog
- **priority**: 手順2で確認した数値（0-4）
- **description**: 組み立てた Markdown 本文を文字列として直接渡す（改行はエスケープせず実際の改行で渡す）
- 必要に応じて `labels`, `project` を付与

複数チケットの場合は、起票後に依存関係（blocks / blocked-by）も設定する。

### 4. 結果報告

作成された Issue の ID と URL を報告する。

作成に失敗した場合は、エラーメッセージをユーザーに報告し、手動作成のための情報（title, description, priority）をまとめて提示する。

## description テンプレート

```markdown
## 概要 (Summary)

[誰が、どの文脈で、何に困っている / 何をしたいか]
[この Issue で解決・達成したいこと]

## 受け入れ要件 (Acceptance Criteria)

- [ ] [要件1]
- [ ] [要件2]
- [ ] [要件3]

## 実装の補足情報 (Implementation Notes)

[技術系: アーキテクチャ・変更箇所・制約 / 機能系: 仕様・振る舞いレベルの補足のみ]

## テスト観点 (Test / QA Notes)

- [確認手順1]
- [エッジケース1]

## 関連情報 (Reference)

- PRD: [リンク]
- Figma: [リンク]
```

## 重要

- テンプレートのセクション構造は必ず維持すること
- 起票は必ず MCP（`mcp__linear-server__save_issue`）で行う。CLI（`linear` コマンド）は使わない
- **技術系 Issue**（ライブラリ更新・導入、リファクタリング等）の場合、コードベースを調査して実装の補足情報を充実させること
- **機能系 Issue**（新機能、機能改善等）の場合、仕様・振る舞いの記載にとどめ、具体的なコード修正箇所は記載しないこと
- 表記ルール（造語ID・節番号・略号・抽象名詞タイトルの禁止）を必ず守ること
